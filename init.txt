
POLICY SCOPE, AUTENTICAZIONE E RATE (v31.79)
---------------------------
- Lo scope attivo usa origin esplicite; authorization.allow_same_host_ports (default false) puo' ammettere servizi HTTP/HTTPS su porte diverse dello stesso hostname esatto, anche con cambio HTTP<->HTTPS. Con authorization.discover_same_host_services=true la discovery puo' inoltre cercarli proattivamente con un sweep TCP generico bounded; il flag richiede allow_same_host_ports=true e non autorizza hostname sibling.
- Un href, iframe, script, XHR/fetch o redirect verso un altro host NON estende lo scope. I suffissi DNS non autorizzano attacchi.
- La console distingue gli URL esterni scartati dagli scanner dalle normali subresource esterne caricate da Chromium per rendering/autenticazione; queste ultime sono segnalate ma non diventano casi di active testing.
- Login e SSO sulla stessa origin autorizzata restano testabili; non esistono eccezioni hardcoded per nomi/path di login.
- Un IdP esterno attraversato dal browser per completare il login non diventa target senza autorizzazione esplicita.
- Qualunque dataset esterno usato per validazione o confronto resta fuori dal runtime: non viene usato come seed, input del planner, source di porte o guida per gli scanner.
- execution.request_rate e' il parametro configurabile: default=10 req/s se omesso, range intero accettato 1-50. Valori >50, <1, non numerici o non finiti tornano al default 10 con RATE WARNING in console e annotazione nel report/Results Data. SECOPS_MAX_REQUEST_RATE e' il valore normalizzato propagato ai processi child. Il limite vale PER SINGOLO assessment/processo: Deterministic e Agentic eseguono gli specialisti attivi di quel run strettamente in sequenza, ma due assessmentRunner avviati separatamente hanno pacer indipendenti e il progetto non impone un token bucket globale alla VM. Se si lanciano piu' assessment in parallelo, l'operatore puo' abbassare execution.request_rate in ciascun config. La concorrenza interna bounded di singoli tool non equivale a parallelismo tra scanner dello stesso assessment. Cambiare il rate modifica il ritmo, non i budget/ceiling di copertura. Due assessment possono essere eseguiti insieme: i loro pacer restano indipendenti. Nel deployment standard condividono pero' un unico daemon ZAP, il cui stato di sessione/mode/Replacer/scanner e' globale; per questo solo le chiamate ZAP vengono messe in coda e serializzate. Il secondo ZAP puo' attendere boundedly circa un budget ZAP precedente e, ottenuto il lock, riceve il proprio timeout completo. Per ZAP realmente paralleli servono daemon/porte ZAP separati per assessment. Anche l'endpoint MCP unificato e' condiviso in modo esplicito: ogni assessment registra una lease di processo, lo startup sulla porta 8100 e' protetto da lock inter-processo e il processo che ha creato il server non lo termina mentre esistono altre lease vive. L'ultimo assessment rilascia il singleton; il fingerprint del sorgente continua a impedire l'uso silenzioso di un server MCP caricato da codice diverso.
- Il server MCP unificato espone un fingerprint dei sorgenti congelato all'avvio: prima di riusare una porta MCP gia' aperta, l'orchestratore verifica LIVE che il processo serva la stessa versione dei sorgenti. La verifica viene ripetuta a ogni attach a un listener gia' esistente, anche se quell'endpoint era stato verificato in precedenza nello stesso assessment, quindi la sostituzione del processo sulla stessa porta non eredita una fiducia cached. Un server SecOps con fingerprint diverso o un servizio estraneo sulla porta viene rifiutato, non riusato silenziosamente. La verifica e' portabile Linux/macOS/Windows.
- Le identita' Authorization/BOLA sono isolate: ogni credential_ref conserva il proprio cookie/storage/OIDC state e non eredita il registry di un'altra identita'. I config possono combinare piu' cookie, piu' coppie username/password browser/OIDC o un mix fino a 16 identita' per servizio; --secondary-cookies resta solo il confronto aggiuntivo della modalita' CLI diretta.
- Gli ID di assessment/report sono collision-resistant anche tra processi simultanei e il runner raccoglie soltanto artifact col proprio report id: il glob di prefisso e' solo una ricerca filesystem, poi il report_id deve coincidere esattamente con quello del job oppure essere la sua variante `_Emergency_`. JSON/HTML/review/Results Data, pubblicazione PDF, configurazione/runtime generati e cache token provider usano scritture atomiche dove applicabile; su POSIX la cache token viene inoltre mantenuta privata 0600 quando supportato.
- SQLMap e Commix richiedono le copie repository gestite dall'initializer in ~/.local/opt anche se esiste gia' un comando omonimo nel PATH; Nuclei valida in setup l'intero contratto CLI usato dal wrapper, incluse le opzioni DAST/fuzzing.

     python .\assessmentRunner.py --target https://app.example.org/ --orchestrator deterministic --mode balanced --authorized

     --cookies "<COOKIE_HEADER>"

   IMPORTANTE: la modalita' diretta --target NON accetta username/password del target.
   Non esegue il login OIDC per creare una sessione. Se possiedi soltanto username e
   password del sito devi usare --config con una credenziale di login supportata, per
   esempio kind=browser_oidc. In alternativa devi procurarti prima un cookie valido.

   La discovery espande la superficie autorizzata usando HTML, link, form, query string,
   endpoint JavaScript e richieste document/XHR/fetch osservate da Chromium. Origini diverse
   dalla principale entrano solo se dichiarate esplicitamente nello scope autorizzato.

C) NUOVA APPLICAZIONE - CONFIGURAZIONE
   Usa --config quando hai piu' host, porte, base path o identita'. Usalo anche quando
   devi creare la sessione da username/password oppure quando alcuni URL precisi devono
   essere garantiti come punti di ingresso.

   Ogni servizio HTTP/HTTPS puo' essere descritto con service.url completo oppure con
   asset.host/IP, porta, protocollo e base_path.

   In una normale applicazione non serve elencare tutte le pagine interne. Basta la radice
   o il base path e la discovery cerca il resto usando link/form, DOM renderizzato, menu dinamici,
   JavaScript e traffico browser osservato. Se invece ricevi un elenco di URL che devono essere
   garantiti come punti di ingresso autorizzati, inserisci un servizio per ciascun URL.
   Se piu' entry URL descrivono lo stesso servizio logico e condividono policy di sicurezza/autenticazione,
   il runner puo' coalescerle a runtime mantenendole tutte come entry point. Dataset esterni usati soltanto
   per validare i risultati restano fuori dal config e dall'esecuzione.

   Prima di avviare gli scanner esegui un dry-run:
     python .\assessmentRunner.py --config .\configs\platform.example.json --orchestrator deterministic --mode balanced --dry-run --authorized

D) AUTENTICAZIONE DA CONFIG
   Una credenziale kind=browser_oidc puo' usare un cookie gia' disponibile oppure
   username/password del target. Il runner trasforma il login riuscito in una sessione cookie
   e passa quella sessione agli orchestrator esistenti. Con allow_same_host_ports=true, su una nuova
   porta dello stesso hostname/schema l'ordine resta: cookie esistente -> session probe -> storage
   browser/OIDC -> username/password gia' risolti, senza un nuovo prompt nel child. Se il cookie grezzo
   viene rifiutato in modo conclusivo su quella porta, la coppia cookie+origin viene ricordata e non viene
   riprovata da ogni scanner successivo; una sessione riparata/origin-specifica prende il suo posto.

   Se optional=true e il login non e' disponibile o fallisce, il job continua in anonimo.
   Se usi --auth-only, invece, la sessione autenticata e' obbligatoria e il job viene bloccato
   quando il login non riesce.

E) QUALE MODALITA' CONVIENE
   fast      = smoke test o diagnostica breve
   balanced  = scelta consigliata per il normale assessment
   deep      = copertura e budget maggiori. Usarla dopo aver verificato target, login e scope

   Deterministic = percorso a ordine fisso e riproducibile, consigliato per la prima esecuzione.
   Agentic       = planner AI e analisi AI finale delle evidenze.
   assessmentRunner.py = percorso consigliato per l'uso normale e per i config.
   orchestrator*.py diretto = utile soprattutto per target singoli e diagnostica manuale.

F) COME VEDERE COSA STA FACENDO
   Durante il run il terminale mostra fase, tool, target, stato, limiti e diagnostica.
   Deterministic segue la pipeline fissa. Agentic mostra anche i round e le azioni scelte.
   PARTIAL, time_limit, skipped ed error descrivono l'esecuzione o la copertura. Non indicano
   automaticamente la presenza o l'assenza di una vulnerabilita'.

   Dopo un run con assessmentRunner.py il riferimento piu' completo e':
     .\reports\Assessment_Results_Data_<ID>.json

   Contiene risultati scanner, coverage, discovery, diagnostics, finding, contesto,
   planner audit, decisioni Agentic e analisi AI quando presenti.

G) DOVE SONO I RISULTATI
   .\reports\SecOps_*.pdf          -> report leggibile
   .\reports\SecOps_*.html         -> report navigabile
   .\reports\SecOps_*.json         -> dati tecnici del report

   .\reports\Assessment_Results_Data_<ID>.json -> dataset redatto autosufficiente del runner

   assessmentRunner.py stampa i percorsi esatti alla fine sotto "Assessment final artifacts".

Per tutti i test usa esclusivamente target autorizzati. Su target non locali mantieni

0. LEGENDA TOKEN/CREDENZIALI

In questo documento la parola "token" indica due concetti di accesso diversi e senza
relazione tra loro. Ogni menzione successiva di "token" in questo file e' etichettata con
uno dei due marcatori qui sotto, cosi' e' sempre chiaro a quale accesso ci si riferisce:

TARGET REMOTO CONFIG-DRIVEN
---------------------------
Mantieni mapping host, servizi autorizzati e riferimenti alle credenziali nel config dell'assessment o
nell'ambiente dell'operatore. La documentazione e il codice generico non devono incorporare host, IP,
endpoint, porte o dataset di validazione appartenenti a un target specifico.

Per una credenziale browser_oidc l'ordine di riuso e' generico:
- un rifiuto username/password sul form della target origin o sull'issuer OIDC gia' pinnato puo' offrire un solo tentativo di correzione nel parent;
- un rifiuto su un realm OIDC esterno non ancora pinnato NON dimostra che le credenziali locali del dashboard siano errate: viene registrata la destinazione senza query/segreti, vengono provati gli altri entry point primari e non viene richiesto di reinserire inutilmente la stessa password;
- per applicazioni che richiedono intenzionalmente un provider OIDC esterno fisso si puo' impostare credential.oidc_issuer con l'authorization endpoint atteso; il riuso successivo resta vincolato a quell'issuer/realm.
  1. cookie applicabile alla destinazione, se presente;
  2. validazione con session probe;
  3. storage state browser/OIDC gia' disponibile;
  4. username/password originali gia' risolti dal runner, soltanto se il flusso di login li richiede.
Un cookie_env viene prima canonicalizzato; se required_cookie_names e' configurato, il cookie manuale viene
usato soltanto se contiene tutti i nomi richiesti. Un cookie incompleto non viene spacciato per sessione valida:
si passa allo storage browser/SSO e poi alle username/password della STESSA identita'. Le credenziali vengono
risolte nel parent runner una sola volta e mantenute in memoria per il job; i child non riaprono prompt.
Il Cookie header grezzo non viene mai copiato su un hostname diverso. Per browser/OIDC la cache del Cookie
header appiattito e' path-aware e conserva il path URL esatto: /app e /app/ sono distinti perche' routing HTTP e
Cookie Path possono differire, mentre query e fragment non cambiano la chiave di cache. Una sessione ottenuta per
/app-a non viene quindi riusata automaticamente per /app-b; lo storage Playwright della stessa identita' puo'
invece essere riusato per ricavare i cookie corretti senza un nuovo login. Su un cache hit il resolved_cookie del
runtime viene riallineato al cookie cached prima di costruire il payload parent->child, evitando fingerprint/storage
mismatch dopo la visita di un altro path. Domain/host-only, Path, Secure e scadenza vengono rispettati; expires=0
resta un cookie scaduto e non viene convertito in session cookie. IndexedDB viene incluso nello storage state quando
supportato. I cookie CHIPS/partitioned restano nello storage browser e NON vengono trasformati in un Cookie header
per scanner HTTP, perche' mancherebbe il contesto top-level della partizione.
Una diversa porta/HTTPS-HTTP dello stesso hostname puo' essere autorizzata dalla policy multi-port, ma il riuso
della sessione resta subordinato alla normale policy Cookie/Storage e alla validazione.

Esempio generico:
  python .\assessmentRunner.py --config .\configs\<assessment>.json --orchestrator deterministic --mode balanced --dry-run --authorized
  python .\assessmentRunner.py --config .\configs\<assessment>.json --orchestrator deterministic --mode balanced --authorized
  python .\assessmentRunner.py --config .\configs\<assessment>.json --orchestrator agentic --max-rounds 2 --mode balanced --require-ai --authorized

Configurazioni target: URL completo oppure host/IP + porta
--------------------------------------------------------
Per un servizio HTTP/HTTPS il config accetta due forme equivalenti:
  1) link completo nel campo service.url, per esempio:
       "url": "https://turismo.example.org/dashboard"
  2) asset.host + service.port; protocol e base_path restano opzionali secondo il caso.
     Se protocol non e' indicato, la porta 443 implica https, le altre porte implicano http.
     Per HTTPS su porte non standard conviene indicare esplicitamente "protocol": "https".

Il campo service.url, quando valorizzato, ha precedenza su host/port/base_path. La forma host + protocol + port e' una forma valida alternativa per descrivere il servizio.
La validazione del config controlla anche i tipi booleani (enabled/auth_only/allow_state_changes/require_ai), max_rounds 1-3 e tutti i nomi presenti in credential_refs; un riferimento inesistente o auth_only=true senza almeno una credenziale viene bloccato gia' nel dry-run. Il loader rifiuta chiavi JSON duplicate, tipi container espliciti errati, nomi credenziali che collidono senza distinzione maiuscole/minuscole e required_cookie_names duplicati/case-duplicati. Ogni servizio puo' dichiarare al massimo 16 identita'; le label devono essere uniche senza distinzione maiuscole/minuscole e sessioni concrete equivalenti (anche se l'ordine delle coppie nel Cookie header e' diverso) non vengono usate come falsi confronti cross-account.

Regola generale per un servizio anonymous-only nel JSON: non impostare credential_refs. Con auth_only=false e una o piu' credential_refs il runner esegue anonymous PIU' un profilo autenticato distinto per ogni identita' disponibile. Con auth_only=true esegue soltanto le identita' autenticate disponibili.
Per `configs/tourist-dashboard.json` lo stato ATTUALE e' anonymous-only perche' al momento non sono disponibili account target: il file corrente non contiene credentials/credential_ref/credential_refs/secondary_credential_ref. Non e' un vincolo permanente del progetto: se in futuro vengono fornite credenziali, si possono aggiungere al config con gli stessi meccanismi generici cookie/browser_oidc senza cambiare gli orchestratori. Il self-test auth/config verifica quindi i contratti generici di autenticazione e non vieta future credenziali per questo target.

Esempio multi-identita' (vedi anche configs/platform.example.json):
  "credentials": {
    "portal_user":   {"kind":"browser_oidc", "username_env":"SECOPS_PORTAL_USER_USERNAME",   "password_env":"SECOPS_PORTAL_USER_PASSWORD",   "cookie_env":"SECOPS_PORTAL_USER_COOKIE",   "login_path":"/app/", "validation_path":"/app/"},

    "portal_admin":  {"kind":"browser_oidc", "username_env":"SECOPS_PORTAL_ADMIN_USERNAME",  "password_env":"SECOPS_PORTAL_ADMIN_PASSWORD",  "cookie_env":"SECOPS_PORTAL_ADMIN_COOKIE",  "login_path":"/app/", "validation_path":"/app/"}

  ... service ...
  "credential_refs": ["portal_user", "portal_editor", "portal_admin"]

Se cookie/username/password non sono disponibili nelle rispettive variabili env, il processo padre interattivo chiede i dati separatamente per OGNI identita' con prompt [AUTH:<credential_ref>]. Le credenziali restano in memoria e non vengono ristampate nei comandi persistiti. SQLMap, Dalfox, Commix, Traversal, IDOR, Browser, Workflow e le altre fasi profile-driven usano ogni profilo separatamente; Authorization/BOLA confronta l'identita' attiva con tutte le altre identita' disponibili. Il suo deadline complessivo per azione non cresce col numero di account: il tempo di richiesta viene suddiviso in modo fair e bounded fra primaria, anonymous e identita' alternative. Lo storage browser/OIDC e il registry di sessione di una identita' non vengono mai ereditati da un'altra. La deduplica delle sessioni usa un fingerprint order-insensitive delle coppie cookie, quindi `A=1; B=2` e `B=2; A=1` rappresentano la stessa sessione e non possono produrre falsa evidenza BOLA. La validazione Authorization mantiene label e cookie come coppie anche se un'identita' opzionale e' assente. Per una stessa credenziale OIDC usata su piu' applicazioni della stessa origin, la cache del Cookie header e' distinta per path applicativo mentre lo storage browser resta riusabile. Il bootstrap dell'issuer OIDC e' disponibile una sola volta per credential_ref: dopo il primo login browser riuscito, le applicazioni successive non possono adottare un realm nuovo se il primo login era locale o un issuer diverso se era OIDC. Credential_ref distinti mantengono issuer indipendenti anche quando riusano volutamente le stesse env username/password. Per realm/provider OIDC differenti usare quindi credential_ref distinti.

Quando piu' service entry condividono la stessa origin, lo stesso path ESATTO e la stessa policy di sicurezza/autenticazione, il runner puo'
coalescerli in un solo job logico e conservare tutti gli URL come entry point iniziali. Il trailing slash e' significativo:
/app e /app/ restano job distinti; varianti che cambiano soltanto query sulla stessa path esatta possono invece condividere
la pipeline completa mantenendo ogni URL come forced entry point. --only <job-id> mantiene la possibilita' di diagnosticare
un servizio singolo. Il reporting aggregato resta utile quando sopravvivono piu' job realmente distinti.

Dry-run consigliato:
  python .\assessmentRunner.py --config .\configs\<assessment>.json --orchestrator deterministic --mode balanced --dry-run --authorized

Esempio architettura complessa:

Mostra entrambe le forme supportate: service.url completo oppure asset.host/IP + porta/protocol/base_path. Le origin aggiuntive sono target soltanto quando sono configurate esplicitamente; non vengono inferite da domini padre o link scoperti. L'esempio mostra tre identita' browser_oidc in credential_refs: se le rispettive env var non sono valorizzate, username/password vengono richiesti separatamente in console per ogni identita'. Ogni sessione diventa un profilo autenticato distinto; l'esempio include anche un servizio non web di inventario e reporting aggregato.

4. AGENTIC
----------
Modelli Agentic supportati (il provider viene scelto internamente):
  snap4city  -> Snap4City, endpoint llama4-agentic-inference
  llama      -> Ollama locale, llama3.1:8b
  qwen       -> Ollama locale, qwen2.5:7b

Llama e Qwen condividono la stessa verifica Ollama, ma la selezione del modello e' esatta:
qwen non viene sostituito automaticamente da llama e llama non viene sostituito da qwen.

Non esiste un'opzione --ai-provider: --model sceglie l'AI e il codice deduce automaticamente
il provider corretto. Quindi snap4city usa Snap4City; llama e qwen usano Ollama.

I comandi assessment Agentic stampati da initScript.py usano Snap4City per default e --require-ai quando Snap4City e' verificato; viene inoltre stampato un comando diretto orchestratorAgentic.py con il backend effettivamente disponibile.

Snap4City FAST (2 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 2 --mode fast --require-ai

Snap4City BALANCED (2 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 2 --mode balanced --require-ai

Snap4City DEEP (3 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 3 --mode deep --require-ai

Alternative locali Ollama:
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model llama --max-rounds 2 --mode balanced --require-ai
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model qwen --max-rounds 2 --mode balanced --require-ai

Con seconda identità:
python .\orchestratorAgentic.py --target <TARGET> --cookies "<PRIMARY_COOKIE>" --secondary-cookies "<SECOND_ACCOUNT_COOKIE>" --auth-only --authorized --model snap4city --max-rounds 3 --mode deep --require-ai

Snap4City rispetta la priorita' del TokenManager Snap4City (1): prima riusa un access token (1) ancora valido in token_stored.json;
se e' scaduto prova il refresh token (1); con credenziali del provider risolte dal file/ambiente usa username/password come ultimo passo normale.
Se snap4city_model_credentials.json manca o contiene ancora placeholder, i placeholder non vengono mai inviati: vengono provati prima access token (1)
e refresh token (1) gia' salvati e solo se entrambi non sono utilizzabili, con terminale interattivo, vengono chiesti username/password
per quel processo. La password viene letta senza echo e le credenziali inserite non vengono scritte automaticamente nel JSON.

Senza --require-ai, se il planner AI fallisce può essere usato il piccolo fallback deterministico discovery-derived (massimo
3 azioni sicure per round). Con --require-ai il fallback del planner è disabilitato e il run fallisce se planning/analysis AI
non completano correttamente. Durante un assessment gia' avviato un fallimento del backend AI non cambia automaticamente
provider o modello: Snap4City, Llama e Qwen restano selezioni distinte. Il fallback Snap4City -> Ollama descritto nella sezione
di inizializzazione avviene soltanto durante la preparazione, prima di avviare l'assessment.

Il planner riceve candidati derivati dalla discovery e li seleziona in base al
valore informativo atteso. Può differire controlli ridondanti e non usa una
checklist minima. Ogni azione passa dagli stessi validator del Deterministic. Al termine, un nodo AI separato
rivaluta severity, descrizione, impatto, conseguenze potenziali, azioni di recovery/ripristino e remediation
dei finding usando soltanto l’evidenza degli scanner; categoria, verification status ed evidenza non possono
essere modificati. Se il tool aveva gia' fornito questi testi, l'originale resta nel riquadro di audit del report.

DISCOVERY E COPERTURA DINAMICA
-----------------------------
Per default initScript.py installa Playwright Chromium, su Linux richiede anche le dipendenze host
con `python -m playwright install --with-deps chromium` e verifica un avvio headless reale. Se questa
verifica fallisce, l'inizializzazione fallisce invece di lasciare il Browser verifier in stato
`missing_playwright_browser`. Solo `--skip-browser` disattiva esplicitamente questa garanzia.

La discovery combina crawler HTTP, form/query, link e attributi di navigazione HTML, endpoint letterali
inline/JavaScript e una coda Chromium. Il browser osserva document/XHR/fetch, estrae href/src/action/formaction
e comuni data-href/data-url/data-link/data-src dal DOM renderizzato e puo' espandere in modo bounded solo
menu/dropdown/collapse non contenuti in form e privi di etichette distruttive. Il request guard continua a
bloccare navigazioni non GET/HEAD/OPTIONS. I valori di parametri di routing come redirect/linkUrl/page/file/path
che identificano moduli interni entrano nella firma semantica e la destinazione annidata sicura viene reinserita
nella coda; due moduli diversi restano candidati distinti anche quando condividono lo stesso parametro.
I budget Chromium sono 72/200, 500/1500 e 1000/3000 (base/massimo) in fast/balanced/deep; i controlli menu per pagina sono 16/64/112 e, dopo una espansione riuscita, il DOM viene ricontrollato fino a 3/6/9 pass bounded senza ricliccare i controlli. Il crawler HTTP usa 120/220, 750/1375 e 1500/2750 pagine utili; gli asset JavaScript realmente ispezionati sono 128/800/1500. Dopo il budget HTTP base, l'overflow continua solo finché il candidato successivo mantiene almeno il 75% del cutoff del set base. La coda garantisce inoltre una prima opportunita' a ogni nuova famiglia applicativa runtime, definita da origin + struttura iniziale del path, prima di tornare ripetutamente su famiglie gia' visitate; l'overflow bounded conserva una piccola reserve anche per famiglie scoperte tardi. Il log segnala separatamente base, overflow, massimo, tentativi e candidati rimasti. Gli stessi indicatori principali vengono riportati anche nella Discovery summary del report, insieme al numero di famiglie applicative visitate e all'esito aggregato dell'autenticazione runtime delle sibling. L'origine primaria mantiene un bonus generico nel ranking, così le sibling origin esplicitamente autorizzate restano esplorabili senza sottrarre facilmente le pagine più rilevanti al target principale. Le varianti OAuth/OIDC puramente volatili (state, nonce, session_code, tab_id, execution, challenge) e i callback applicativi con combinazioni transienti state/code/session_state/iss vengono mantenuti come evidenza ma de-prioritizzati e limitati a una sola variante per shape di route durante discovery, cosi' non saturano la coda. I callback transienti non entrano nei pool injection/traversal/workflow, mentre la route login/SSO stabile senza query resta disponibile per l'autenticazione. Nel profilo authenticated Chromium importa direttamente lo storage state browser salvato quando disponibile e, al termine, conserva quello aggiornato: cookie Domain/Path/Secure/host-only e stato SSO/local storage non vengono appiattiti in un Cookie header origin-wide durante la discovery. Le XHR/fetch osservate non consumano un ulteriore budget di pagine e possono generare
request contract. Per le richieste realmente inviate vengono registrati anche status/content-type della response
o requestfailed, cosi' il planner distingue endpoint raggiunti da 404/410 senza scartare 401/403. Le risposte HTTP 404/410 restano nei warning e nel report, ma non consumano il budget di pagine utili del crawler, non diventano seed HTML per Chromium/ZAP e, dopo conferma dello status, non generano request contract specialistici. Un limite separato di tentativi HTTP pari a 1,75x/2,0x/2,0x del massimo utile in fast/balanced/deep evita che grandi insiemi di link morti causino richieste non bounded senza troncare prematuramente il crawl utile. Gli abort/timeout/navigation context distrutti di Chromium ricevono al massimo un retry bounded di navigazione o estrazione DOM e i retry sono riportati nei diagnostics. Se esistono pagine HTML ma Chromium conclude con 0 navigazioni, la console mostra un BROWSER WARNING e porta gli errori Playwright/runtime/navigation prima dei normali 404/410. Nel Deterministic la discovery Playwright sincrona viene eseguita in un worker thread, evitando l'uso della Sync API dentro l'event loop asyncio di LangGraph. Se il numero di navigazioni raggiunge il limite del profilo, la console stampa inoltre la saturazione usato/budget. Le richieste
browser non-GET e le rotte distruttive vengono intercettate prima dell'invio:
il body puo' diventare request contract con metodo e parametri reali; GET/POST vengono poi consumati dai tool
compatibili, mentre gli altri metodi restano tracciati come superficie osservata.
POST e JSON restano request contract di prima classe: non vengono eliminati per rendere la discovery sicura.
La coda deduplica le varianti ordinarie ma conserva valori semanticamente diversi dei parametri che selezionano
route/file/moduli interni; applica quote per origin e penalizza asset statici, vendor/chunk, paginazioni/archivi.
Il runner puo' usare login_path/validation_path gia' presenti nella credenziale come discovery seed ordinari,
soggetti ai normali budget: non vengono considerati entry point forniti e nessun dataset esterno di validazione viene
iniettato nel config, nella discovery o nel planner. login_path e' opzionale: quando manca sul target iniziale, Chromium usa una
piccola discovery pre-auth bounded sulla stessa origin, seguendo soltanto candidati GET non distruttivi e cercando
form/controlli di login o redirect OIDC generici. Se non trova un candidato migliore usa target/root; questa fase
non invia form, non amplia lo scope e con un login_path esplicito non viene eseguita. Non puo' indovinare una route di login completamente scollegata/non esposta dai pochi link same-origin visitati: in quel caso login_path resta un hint utile.
Nei credential browser_oidc, reuse_on_authorized_siblings=true abilita il riuso delle credenziali gia' risolte soltanto sulle altre destinazioni gia' autorizzate. Nel PRIMO login primario, se non esiste ancora un issuer memorizzato, il browser puo' apprenderlo soltanto da una vera richiesta OAuth/OIDC di autorizzazione osservata nello stesso tentativo; le credenziali possono essere compilate soltanto sull'authorization endpoint stesso oppure su una route login/session/authenticate della stessa origin del provider. Dopo il bootstrap, ogni riuso resta vincolato allo stesso authorization endpoint/provider. Se il login primario era invece un form locale, un nuovo realm OIDC osservato in seguito non riceve automaticamente le credenziali. Una normale pagina applicativa non viene mai usata come issuer sintetico e il riuso non amplia lo scope. Schema+hostname+porta effettiva definiscono la origin. authorization.allow_same_host_ports=true ammette altri servizi HTTP/HTTPS soltanto sullo stesso hostname esatto, anche con porta o schema differente; non autorizza sibling DNS. authorization.discover_same_host_services=true, valido solo insieme al flag multi-port, esegue una service discovery proattiva host-level. L'ordine e' generico e target-agnostic: prima un set compatto di porte web/applicative comuni, poi i database di servizi disponibili a runtime, infine un campionamento stratificato sull'intervallo TCP 1-65535. I ceiling di candidati restano 4096/32768/65535 in fast/balanced/deep, ma la sola ricerca porte condivide anche un budget wall-clock globale di 240/900/1500 secondi per processo. L'hostname iniziale puo' consumare al massimo 120/450/750 secondi, lasciando il resto agli hostname nuovi. Gli hostname esatti osservati successivamente vengono inclusi soltanto se erano gia' autorizzati; fino a 8/32/128 hostname aggiuntivi condividono un pool di espansione separato da 4096/32768/65535 candidati e il tempo globale rimasto, ripartendo equamente tra gli host ancora da provare sia il tempo sia i candidati residui; tempo non consumato e candidati non sondati rientrano nel pool e vengono redistribuiti tra gli host restanti, quindi nessun host può assorbire tutto il tempo finché esistono altri host non ancora scanditi. I recrawl autenticati non avviano port scan locali: un unico pass finale dopo l'arricchimento autenticato copre gli hostname autorizzati emersi solo dopo il login. I risultati TCP/service sono riusati per hostname esatto tra profilo anonimo e autenticato, quindi lo stesso host viene sottoposto allo sweep al massimo una volta per processo di assessment; cambia soltanto il recrawl applicativo con la sessione del profilo corrente. In questo modo 20 superfici nuove non moltiplicano il port scanning in ore. TLS (Transport Layer Security) e' il protocollo crittografico usato da HTTPS per cifrare la connessione e validare il certificato del server. Un servizio entra nella superficie web solo dopo una risposta HTTP riconoscibile; HTTPS viene classificato con handshake TLS bounded e probe HTTP. Porte TCP aperte ma non confermate HTTP/HTTPS restano inventario "open TCP / web unconfirmed": non sono finding e non vengono dichiarate sicuramente non-web. Anche la risoluzione DNS e la scelta dell'indirizzo tra host multi-A/dual-stack sono vincolate dal medesimo deadline locale, quindi retry del resolver non possono sfuggire al budget globale 240/900/1500 s. Lo stesso deadline copre pacing, connect TCP, handshake TLS e classificazione HTTP: allo scadere non parte nessun passaggio successivo oltre il tempo residuo. Una classificazione interrotta resta diagnostica `classification-deferred` e non viene confusa con una porta sicuramente non-web. Il resolver effettua retry bounded soltanto per errori transitori; per ogni porta candidata possono essere provati tutti gli indirizzi A/AAAA risolti senza moltiplicare il candidate-port budget, e il probe HTTP usa HEAD con fallback a GET minimale se HEAD non produce una risposta HTTP utilizzabile. Un hostname autorizzato fallito prima del primo probe reale resta ritentabile in un pass successivo bounded; soltanto un cache hit o copertura di probe effettiva evita uno sweep duplicato. I ceiling di candidati sono massimi e la copertura reale viene riportata tramite ports_probed, candidati differiti, tentativi TCP, numero di indirizzi risolti e classificazioni differite. Nessun dataset esterno di validazione viene consultato. Per una root HTTPS autorizzata il crawler prova prima la validazione TLS normale; solo un errore di trust/certificato abilita un singolo retry della stessa URL con verify disabilitato, registrato come diagnostica. Gli errori di protocollo/cipher non attivano questo fallback. Gli scanner attivi sono eseguiti strettamente in sequenza sia dal Deterministic sia dall'Agentic. execution.request_rate vale 10 req/s per default se assente e accetta valori interi 1-50; un valore fuori intervallo/non valido torna a 10 con warning in console e nel report. SECOPS_MAX_REQUEST_RATE contiene il valore effettivo propagato ai wrapper. La policy e' per singolo assessment/processo e non e' un limite globale della VM: due runner indipendenti hanno due pacer indipendenti; per eseguirli contemporaneamente si riduce il rate di ciascun config se necessario. Session probe, target preparation, logout verifier e pre-verifiche HTTP sensibili seguono redirect soltanto sulla origin iniziale; la discovery generale applica invece l'intera policy autorizzativa, incluso allow_same_host_ports quando abilitato. Arjun (con --disable-redirects), Nuclei (-dr), SQLMap (ignoreRedirects) e Commix (--ignore-redirects) non seguono redirect autonomamente; --disable-redirects blocca davvero tutti i redirect interni ad Arjun. Per i casi GET il wrapper Arjun risolve prima una catena bounded no-follow. Lo scope multi-port puo' autorizzare anche HTTP<->HTTPS sullo stesso hostname esatto, ma il resolver non trascina un Cookie grezzo attraverso un cambio di schema/origin: in quel caso rinvia la destinazione alla discovery/runtime-auth centrale. Se il Location punta a un hostname diverso ma esplicitamente autorizzato, il wrapper NON trascina il cookie corrente su quell'host: la destinazione resta alla discovery centrale, che puo' applicare la sessione corretta. I non-GET non vengono ripetuti solo per risolvere redirect; la discovery HTTP/Chromium segue invece in modo bounded le catene che restano nella policy autorizzativa: i redirect same-origin sono normali, una origin esplicita e' ammessa e, con allow_same_host_ports=true, e' ammessa anche una porta o uno schema HTTP/HTTPS differente sullo stesso hostname esatto; le destinazioni autorizzate scoperte vengono rimesse nella selezione, quindi il no-follow dei processi esterni conserva le normali destinazioni applicative di redirect scoperte in-scope; i comportamenti interni a un singolo scanner/template che richiedono autonomamente un redirect restano invece intenzionalmente soppressi quando il tool non offre una allow-list exact-origin; ZAP non segue redirect nel seeding diretto, usa un context ancorato alla exact-origin, active scan in-scope-only e Protected mode; la native active scan viene abilitata solo se ZAP accetta thread-per-host=1 e il delay derivato da execution.request_rate; se uno dei due controlli di pacing non e' disponibile, la native active scan viene disabilitata fail-closed e il risultato resta PARTIAL, mentre la proxy verification con pacer di progetto puo' continuare; Nikto non usa -followredirects e puo' iniziare soltanto dalla destinazione finale raggiunta dal probe di riferimento same-origin; FFUF non abilita redirect e Dalfox mantiene il proprio default no-follow. Un session probe bloccato su redirect cross-origin o fermato dal limite bounded di redirect same-origin resta inconclusivo e non viene contato come sessione autenticata. Anche Traversal/LFI usa la stessa guardia redirect degli altri verificatori. La console emette [SCOPE] quando osserva URL/origin esterne e specifica che non sono state messe in coda per active testing. Nei redirect bloccati il riepilogo usa la destinazione esterna rifiutata, non la pagina in-scope che ha emesso il Location. Le stringhe URL letterali complete escapate in HTML/JavaScript vengono normalizzate, mentre frammenti incompleti come http\:/ vengono scartati invece di diventare falsi path relativi. Anche il Browser XSS/workflow verifier riceve execution.request_rate, spazia le navigazioni document e applica la stessa policy di scope (incluse le porte stesso-host quando abilitate), bloccando/diagnosticando le destinazioni non autorizzate; le subresource browser necessarie al rendering non sono un token bucket globale di ogni richiesta di rete.
Deterministic esegue la discovery Playwright sincrona in worker thread quando il nodo LangGraph e' dentro asyncio. Agentic usa inoltre discover_target_sync_safe(): il percorso CLI normale e' sincrono, ma se la stessa discovery viene riusata dentro un event loop viene spostata automaticamente in un worker prima di entrare nella Playwright Sync API. Oltre ai ceiling di navigazioni, ogni invocazione Chromium ha anche un guard wall-clock globale derivato come max(120 s, 4 s x budget base effettivo di navigazione); elapsed, budget ed eventuale esaurimento vengono salvati nelle diagnostiche/report, evitando che navigazioni/DOM lente rendano il crawl temporalmente illimitato. I tentativi runtime di autenticazione su origin/applicazioni aggiuntive condividono un budget per pass di 180/720/1800 s in fast/balanced/deep; le destinazioni non raggiunte entro il deadline sono differite. In caso di fallimento vengono marcati come tentati solo gli entry point realmente visitati, non tutti quelli candidati.

ZAP: fast=targeted, balanced=prioritized, deep=full bounded; la modalita' passiva resta per i soli
controlli diagnostici. L'inventario active usa API Python/JSON e fallback curato; ogni scanner ID viene
abilitato separatamente e il log distingue piano teorico da regole accettate. Le risorse statiche non possono
essere scelte come target active. I request contract parametrizzati restano il piano preferito; se su un'origine
non esiste alcun contract parametrizzato compatibile, ZAP prova comunque un fallback active bounded su massimo
1/2/3 pagine GET applicative sicure in fast/balanced/deep, recurse=false, usando una piccola unione di regole
installate per reflected-XSS, SQL injection generica, traversal e command injection. Non viene quindi avviato uno
spider active ricorsivo dell'intero dominio. PARTIAL/no_active_scan_rules_enabled resta solo quando non esiste
ne' un piano parametrizzato compatibile ne' una pagina GET sicura con almeno una regola curata effettivamente
abilitabile. Le observation passive conservate sono 180/800/1400 in fast/balanced/deep; i security finding non
sono soggetti a questo tetto di observation. Richieste equivalenti con stesso metodo, path e parametri restano deduplicate.
Nuclei: balanced e deep possono usare request contract per DAST gap checks bounded, distribuiti prima tra famiglie applicative distinte e poi per score. Il DAST prova prima
l'input Proxify JSONL; se il runtime Nuclei lo rifiuta, gli stessi contract GET/POST vengono ritentati
in YAML MultiDoc Proxify. Solo se entrambi i formati request-shaped falliscono si usa la lista URL per i GET compatibili;
i POST non rappresentabili restano esplicitamente non coperti invece di essere dichiarati testati.
Prima del prompt Agentic, Python trasforma la discovery in AZIONI CONCRETE: ogni candidato identifica profilo, tool e target/request contract esatto. Python elimina soltanto lavoro fuori scope, non sicuro, incompatibile o duplicato e normalizza i dati necessari all'esecuzione. Il planner AI decide direttamente quali action ID Axxxx eseguire e ne stabilisce l'ordine di priorita'. Due request dello stesso tool sono decisioni indipendenti: l'AI puo' scegliere una SQLMap request importante e scartarne un'altra, oppure scegliere un'azione importante di un tool anche quando altre azioni dello stesso tool hanno valore basso.

Il catalogo delle azioni viene ordinato con interleaving tecnico tra profili/tool per evitare che una famiglia molto numerosa monopolizzi la prima chiamata al modello; ogni candidato valido viene comunque presentato una volta al planner. I valori 64/96/128 in fast/balanced/deep sono il massimo numero di AZIONI CONCRETE descritte in una singola chiamata AI. Esempio: 230 candidati in balanced producono normalmente 96+96+38; tutti e 230 vengono giudicati dall'AI. Se un batch particolarmente ricco supera il context window bounded, viene suddiviso in batch piu' piccoli senza eliminare candidati.
Granularita': l'AI decide ogni AZIONE DELL'ORCHESTRATORE. Per uno specialista mirato l'azione contiene normalmente request contract e parametri esatti; per scanner broad come ZAP/Nuclei/Nikto l'azione e' una singola invocazione bounded su un target/origin autorizzato. Le singole probe HTTP interne allo scanner restano responsabilita' dello scanner stesso: non sono ulteriori decisioni Python nascoste.

Python puo' calcolare score/hint di discovery per ordinamento stabile, deduplica dei contratti esattamente equivalenti e descrizione dell'evidenza, ma tali score NON decidono l'esecuzione Agentic. Il catalogo candidato non viene tagliato usando il budget di esecuzione per-tool prima dell'AI. Ogni batch assegna alle azioni selezionate una ai_priority 0-100; dopo tutti i batch Python ordina globalmente le selezioni per questa priorita' (con ordine del modello come tie-break) e solo allora applica la capacita' di ammissione globale risolta per il round. La priorita' AI resta autorevole sia per selezione sia per l'ordine globale di esecuzione. L'executor non riordina gli attacchi per tool/profilo, non promuove automaticamente FFUF/Arjun e non aggiunge azioni non selezionate. FFUF e Arjun sono producer di discovery solo nel flusso dati: quando una loro azione selezionata raggiunge la posizione stabilita dall'AI, il relativo enrichment viene unito immediatamente prima dell'azione successiva. Il planner e' quindi istruito a dare priorita' alta ai producer utili quando l'espansione puo' migliorare il lavoro successivo; ZAP/Nuclei e gli altri consumer discovery-aware che vengono dopo vedono la superficie aggiornata senza che Python sposti un producer a priorita' inferiore davanti a un'azione piu' importante. Le nuove azioni specialistiche concrete generate dall'enrichment restano disponibili al round di feedback successivo. Python puo' fermarsi al tetto di traffico/tempo, ma non sostituisce un'azione esclusa con un attacco diverso scelto autonomamente. I valori TEST/FAST/BALANCED/DEEP 24/120/320/480 sono capacita' di riferimento, non hard cap di copertura. TEST resta volutamente bounded come smoke profile; in FAST/BALANCED/DEEP la capacita' normale del round diventa min(E, max(reference, ceil(E/R))), con E=azioni eleggibili rimanenti e R=round rimanenti. Se l'AI richiede request_adaptive_extension=true, puo' essere ammesso fino a un ulteriore +12.5% della capacita' normale risolta, sempre bounded dal lavoro eleggibile. Nessuna di queste capacita' obbliga Python a scegliere o aggiungere attacchi: l'AI resta responsabile di selezione e priorita', mentre il vero hard stop e' il wall-clock.

FFUF, ZAP, Nuclei, Session, Nikto, JWT, SQLMap, Dalfox, Commix, Traversal, IDOR, Authorization, Browser, Workflow e Interactsh vengono rappresentati come azioni concrete compatibili con la discovery. Python esegue le azioni selezionate dall'AI dopo i controlli di scope, safety e risorse. Se il planner fallisce e --require-ai NON e' attivo, viene usato il fallback deterministico di emergenza sotto le stesse policy; con --require-ai il run termina con errore. Deterministic resta un orchestratore separato con pipeline fissa e riproducibile. Le fasi post-planning di verifica/completion (conferma Chromium exact-parameter, safe-surface sweep e controlli lifecycle/sessione) operano deterministicamente per integrita' dell'evidenza e safety, dopo la selezione delle azioni di attacco.

Lo scope autorizzato e lo scope delle credenziali sono separati. Un Cookie header grezzo non viene mai copiato su un hostname diverso; se authorization.allow_same_host_ports=true puo' essere provato anche su un'altra porta autorizzata dello stesso hostname/schema, perche' i cookie HTTP non sono port-scoped, ma deve superare il normale session probe. Se viene rifiutato, il sistema prova lo storage browser/OIDC e infine username/password risolti dal runner, senza prompt nel child. Se il provider rifiuta esplicitamente username/password sul target primario o su un issuer gia' pinnato, il runner NON reinvia automaticamente le credenziali: la credenziale opzionale viene esclusa (oppure quella richiesta fa fallire il job) dopo quel singolo submit. Questo evita di aumentare i contatori di brute-force/lockout quando il provider usa il generico messaggio “invalid username or password” anche durante un blocco temporaneo. Un rifiuto su un realm OIDC esterno non ancora pinnato non dimostra invece che le credenziali locali siano errate: vengono provati gli altri entry point primari senza un secondo prompt. Errori provider di lockout/policy/servizio non provocano retry automatici. Una sessione riparata specifica per la nuova origin/porta sostituisce il cookie grezzo fallito nei test successivi. Lo storage browser conserva Domain/Path/Secure e non autorizza nuove origin. Login e SSO sulla origin target restano testabili.
Le policy hard comuni a Deterministic e Agentic vengono applicate a ogni profilo: scope/cookie isolation, gestione 404/410, limiti Chromium, state-change gate, compatibilita' dei request contract, fallback active ZAP, input bounded dei wrapper e verifica XSS finale. Ranking, cap strutturali e overflow dei selector request-level appartengono alla strategia Deterministic; nell'Agentic i corrispondenti score sono hint del catalogo e non cutoff di visibilita'. Anche la verifica XSS finale Chromium usa base/max 12/20, 96/160 e 200/320 candidati PER PROFILO, quindi anonymous non puo' consumare la quota authenticated. I batch AI e le capacita' globali di ammissione restano specifici dell'Agentic: il Deterministic non ha un tetto globale del planner e percorre direttamente i casi selezionati dalla propria pipeline fissa per ciascun tool e profilo.
JWT dispone di massimo 16/64/192 token unici scoperti per profilo in fast/balanced/deep. Il controllo e' economico e locale, per questo il pool puo' essere ampio; in Agentic ogni token valido diventa un candidato d'azione JWT indipendente che il planner AI puo' scegliere quando e' utile. Se lo stesso identico token raw compare in piu' profili/azioni, il verifier viene eseguito una sola volta e il risultato locale viene riusato mantenendo l'attribuzione per profilo. I valori raw restano input locali del verifier e non vengono mostrati in chiaro nel catalogo di azioni del planner AI.
Gli specialisti sui parametri privilegiano API/dati, identificatori/query, POST/JSON e richieste
osservate dal browser rispetto a parametri puramente di navigazione. Il routing e' distinto per profilo:
le route login/SSO stabili restano superficie testabile nel profilo anonimo, mentre nel profilo autenticato
non vengono inviate a SQLMap/Dalfox/Commix/Traversal. Le istanze OAuth/OIDC/callback con parametri transienti
come state/code/session_state/execution/tab_id non entrano nei pool injection/traversal/workflow di nessun profilo;
la corrispondente route login stabile resta utilizzabile dal resolver di autenticazione. Logout/signout/logoff segue la regola opposta: l'anonimo
lo ignora; l'autenticato ne conserva il request contract GET/POST senza eseguirlo durante discovery/scanner e lo
riserva al controllo finale di lifecycle della sessione.
Entrambi gli orchestratori eseguono infine una verifica Chromium candidate-driven sugli XSS ancora non confermati.
Il budget e' separato per profilo e adattivo: base 12/96/200 e massimo 20/160/320 in fast/balanced/deep. L'overflow
si apre soltanto quando il base e' saturo e i candidate rinviati restano almeno al 75% del punteggio di cutoff;
il punteggio deterministico considera corrispondenza del contesto/parametro, evidenza client-side, traffico browser
osservato e prova scanner disponibile. Il browser riceve solo il parametro del finding sorgente e seleziona il request
contract piu' vicino anche in base agli altri parametri del contesto, cosi' candidate sullo stesso path/parametro ma
con linkUrl/pageTitle/linkId differenti vengono verificati separatamente. L'AI non decide l'overflow finale XSS. Esecuzione
del marker => vulnerability con confidence high; reflection senza esecuzione => candidate con severity invariata e
confidence al massimo medium; nessuna riproduzione nel controllo bounded => severity invariata e confidence low.
La severity rappresenta l'impatto potenziale se il finding fosse reale, mentre la confidence rappresenta la forza
dell'evidenza raccolta. L'analisi AI successiva puo' arricchire la descrizione e rivalutare la severity in base
all'impatto, ma non puo' superare il tetto di confidence deterministico del browser: MEDIUM per reflection non
eseguita e LOW per mancata riproduzione bounded. CSS, JavaScript standalone, immagini e font non sono candidati Browser-XSS. Nel Deterministic il passaggio avviene dopo i controlli speciali e prima del report e
non ripete un URL/metodo/parametro gia' verificato con successo nella precedente fase browser/workflow. Nell'Agentic
avviene prima dell'analisi AI e del report.
Dopo gli altri controlli autenticati, il session verifier puo' eseguire un logout scoperto in modo bounded e poi
riusare il cookie osservato sulla pagina protetta: se quel cookie mantiene accesso autenticato viene prodotto
un finding vulnerability confermato (CWE-613); se viene rifiutato l'invalidazione e' verificata; se l'esito non e'
distinguibile il controllo resta PARTIAL. Il logout non viene quindi fuzzato genericamente e non puo' interrompere
gli scanner autenticati precedenti.
Gli URL molto lunghi vengono compattati solo nella stampa terminale (endpoint + numero parametri/lunghezza query); URL completi, request contract ed evidenze restano invariati nei risultati JSON e nei report. La soglia e' configurabile con SECOPS_TERMINAL_URL_MAX.

La pipeline Nuclei seleziona esplicitamente template HTTP custom/ufficiali e request contract HTTP per DAST. Il flag Nuclei -pt e' un filtro sul TIPO DI PROTOCOLLO DEI TEMPLATE (es. http, headless, workflow, tcp, dns, ssl), non una barriera di scope o di porte: -pt http significherebbe eseguire soltanto template di tipo HTTP. Il rate e' derivato da execution.request_rate (default 10 req/s, massimo configurabile 50); DEEP fino a 96 template technology, 160 exposure/misconfiguration

non quote obbligatorie: fingerprint, product gating e timeout possono ridurre il lavoro effettivo.
I timeout Nuclei sono un unico budget wall-clock per azione: 240/3600/7200 s in fast/balanced/deep.
Le fasi non usano secondi hardcoded ma quote del timeout totale, interpolate in base al carico reale. L'inventario ufficiale dei template viene riverificato all'avvio della singola azione: se il path registrato e' stale il wrapper cerca in sola lettura un inventario locale gia' esistente. FAST: direct evidence 38-45%, DAST 45-55%. BALANCED: direct 8-10%, exposure/misconfiguration 22-30%, DAST 34-48%.
DEEP: direct 6-8%, technology 8-10%, exposure/misconfiguration 16-20%, vulnerability/CVE 22-28%, DAST 22-28%.
Cambiare il timeout totale ridimensiona quindi automaticamente tutte le fasi. I fallback DAST JSONL -> YAML -> lista GET
condividono lo stesso deadline DAST: nessun fallback riparte con un timeout pieno. La parte non assegnata resta riserva
per fingerprint/startup/cleanup e per il tempo gia' consumato dalle fasi precedenti; i template e gli endpoint selezionati restano associati alla stessa azione bounded.

La stessa regola di deadline unico vale per i wrapper multi-fase Arjun, FFUF, Interactsh, Commix, Dalfox, SQLMap, Nikto, Traversal, Authorization, Session, Browser, Workflow e IDOR-Forge.

sommare un secondo timeout completo. ZAP usa un unico deadline globale e seed, passive/spider, proxy verification, active scan, reserve e recovery ricevono quote del timeout totale. verifica preventivamente il contratto CLI dei principali scanner per intercettare flag incompatibili prima di un assessment. Il contratto e' centralizzato per Nikto, Arjun, FFUF, Nuclei, Dalfox, Commix, SQLMap e Interactsh. Il preflight e l'audit offline mantenuti nel progetto coprono compilazione/import, compatibilita' CLI, firme/argomenti MCP, timeout/profili, parsing difensivo dei metadati, booleani JSON stretti e fallback degli override numerici SECOPS_* malformati. Nuclei, Nikto e Traversal rifiutano un scan_profile sconosciuto invece di ricadere silenziosamente su balanced. Non vengono dichiarati file self-test standalone che non siano effettivamente distribuiti nel repository. La discovery conserva fino a 8/20/32 varianti value-only per forma di route in fast/balanced/deep, con una sola variante per le forme OAuth/OIDC effimere. Le destinazioni routing HTTP(S) assolute conservano host/path nella firma semantica. Traversal/LFI conserva inoltre valori routing/resource distinti quando selezionano risorse locali differenti; callback remote e pura negoziazione OAuth/OIDC non diventano input LFI. Statici, logout, richieste distruttive, 404/410 osservati e forme incompatibili restano esclusi dai candidati attivi.

Deterministic e Agentic usano la stessa classificazione di compatibilita', scope e safety ma applicano la priorita' in modo diverso.
  - Deterministic usa i punteggi Python e i limiti base/adattivi/live-reserve della tabella del profilo. Il cap strutturale request-level 2/4/6 limita le varianti equivalenti prima dell'esecuzione costosa e la fairness per famiglia applicativa evita che un singolo modulo monopolizzi gli slot.
  - Agentic costruisce invece un catalogo di azioni concrete. Dopo i filtri hard di scope, safety e compatibilita', e la deduplica dei soli contratti esattamente equivalenti dopo canonicalizzazione, ogni request action strutturalmente valida resta visibile all'AI. I punteggi di `_tool_case_priority()`, `_browser_case_priority()`, `_workflow_case_priority()`, `_authorization_case_priority()` e il ranking Arjun sono metadati/evidenza del candidato, non cutoff di visibilita'. L'AI decide gli action ID `Axxxx` da eseguire e assegna la priorita' finale. I ceiling per-tool e globali vengono applicati soltanto dopo la scelta AI, ordinando globalmente le azioni selezionate secondo `ai_priority`, anche quando il catalogo richiede piu' batch di prompt.

Il batching Agentic contiene al massimo 64/96/128 action record per chiamata AI in fast/balanced/deep. Se il catalogo e' piu' grande, vengono eseguite chiamate successive; se un singolo batch eccede il context window, viene ulteriormente suddiviso. Il batching distribuisce il contesto e non scarta candidati. Le origin sibling osservate e gia' autorizzate diventano azioni broad concrete ZAP/Nuclei/Nikto per il planner; la loro presenza nel catalogo Agentic non dipende dal cutoff broad usato dal percorso Deterministic.
`--ai-timeout` e' il tetto AGGREGATO del planning di un singolo round e non viene moltiplicato per il numero di batch. Esiste anche un limite cumulativo per tutto l'assessment, cosi' i round successivi non possono trasformare l'attesa del planner in ore: TEST/FAST/BALANCED/DEEP hanno al massimo 90/1500/2700/3600 secondi totali di planner. Il tempo non usato passa ai round successivi, ma vengono preservate quote utili per i round futuri (FAST 600s, BALANCED 900s, DEEP 900s per round futuro). Dentro un round, i batch successivi mantengono una riserva minima (15/90/180/240s in TEST/FAST/BALANCED/DEEP) mentre un batch corrente insolitamente lento puo' usare il resto disponibile; un batch veloce restituisce subito il tempo non usato. Anche il fallback Ollama chat -> generate condivide la stessa deadline del batch. Con `--require-ai`, l'esaurimento del budget disponibile o il fallimento definitivo di un batch rende incompleto lo stage AI e produce errore invece di lasciare una parte del catalogo non giudicata in modo silenzioso. Un valore positivo esplicito di `--ai-timeout` viene rispettato come tetto del singolo round quando e' piu' piccolo; `0` seleziona il default del profilo, i valori negativi vengono rifiutati e il limite cumulativo del profilo resta comunque attivo.
Anche l'analisi AI finale dei finding ha un tetto aggregato indipendente, cosi' molti batch di finding non possono moltiplicare l'attesa per ore: TEST/FAST/BALANCED/DEEP usano al massimo 60/900/1800/2700 secondi per l'intero stage di analisi. Retry e split dei batch restano dentro tale limite e la riserva del report resta il vincolo esterno.

La port/service discovery e' host-level. Con `allow_same_host_ports=true` e `discover_same_host_services=true`, i ceiling restano 4096/32768/65535 candidati TCP in fast/balanced/deep, ma la ricerca prova prima le porte gia' configurate o osservate a runtime per l'hostname autorizzato, poi le entry HTTP/web dei database servizi locali disponibili e usa il campionamento stratificato sul resto dello spazio solo con il budget residuo. Il wall-clock dedicato alla service discovery e' globale per processo: 240/900/1500 secondi in fast/balanced/deep. L'hostname iniziale puo' usarne al massimo 120/450/750; se HTML, form, script, XHR/fetch o navigazione browser rivelano altri hostname esatti gia' autorizzati, fino a 8/32/128 di essi condividono un pool di espansione separato da 4096/32768/65535 candidati e il tempo globale rimasto. Ogni host nuovo riceve una quota equa del tempo e dei candidati residui calcolata sugli host ancora da scandire e applica lo stesso ordinamento target-agnostic (porte osservate/configurate, database servizi runtime, poi campionamento stratificato); tempo non consumato e candidati non sondati ritornano al pool comune e vengono ridistribuiti, quindi un host non puo' esaurire tutto il residuo mentre altri sono ancora in attesa. I recrawl autenticati eseguono il crawl ma non un proprio port scan; dopo tutti i recrawl viene eseguito un solo pass di espansione sugli hostname autorizzati emersi durante il login/applicazione. I risultati TCP/service sono cached per hostname esatto nell'intero processo, percio' un host gia' scandito nel profilo anonimo viene riusato nell'autenticato senza un secondo sweep. Le nuove root HTTP/HTTPS confermate vengono recrawlate con 24/112/225 pagine per hostname. DNS e selezione dell'indirizzo sono bounded dallo stesso deadline locale. Lo stesso limite copre pacing, TCP, TLS e HTTP: allo scadere non parte un follow-up oltre il tempo residuo. Una classificazione interrotta e' riportata come differita, HEAD ha fallback GET minimale, tutti gli indirizzi A/AAAA possono essere provati per la stessa porta senza aumentare il numero di candidati e un host fallito prima del primo probe reale resta ritentabile nel pass bounded successivo. Un nuovo path sullo stesso hostname non avvia un altro sweep TCP. L'osservazione di un hostname esterno non lo autorizza e il Cookie header grezzo non viene copiato tra hostname.

I wrapper multi-fase condividono un unico deadline per azione. Il watchdog MCP segue il timeout concreto dello scanner con margine di trasporto; Workflow, Authorization, Session, Browser, FFUF e Nuclei accettano i budget previsti dai profili. Arjun rileva la variante CLI installata per output e rate-limit; Nikto usa l'opzione esplicita `-output`; setupTools verifica preventivamente i flag realmente emessi dai wrapper, i metodi ZAP Python usati a runtime e le firme IDOR-Forge necessarie all'assessment, accettando `param` o `parameter` per l'argomento object-reference upstream.

ZAP e Nuclei possono generare molte richieste interne per una singola azione selezionata. Nell'Agentic l'unita' di decisione resta l'invocazione concreta dell'orchestratore: target/origin per gli scanner broad e request contract/parametri per gli specialisti. Una singola azione Nuclei puo' elaborare internamente un batch DAST bounded; questi probe interni appartengono alla stessa invocazione gia' scelta dall'AI. Il report Agentic usa l'eligibility dello stesso catalogo concreto del planner; il report Deterministic usa i selector bounded del percorso fisso.


Init: --with-lab --run --prepare-ai --agentic-model --snap4city-credentials --mode
      --skip-scanners --skip-preflight --skip-browser --require-browser --commands-only

--prepare-ai: all, snap4city, llama, qwen.
Se --prepare-ai e --agentic-model sono entrambi omessi, il valore effettivo e' all.
Se --prepare-ai e' omesso ma --agentic-model e' presente, il valore effettivo di preparazione diventa quel modello.
Con --with-lab e valore all vengono predisposti entrambi i modelli Ollama e verificato Snap4City.
Con snap4city l'initializer non provisiona ne' richiede Ollama se nessun modello locale e' richiesto.
Se --prepare-ai e --agentic-model sono entrambi presenti, all include qualunque modello; una selezione singola deve invece coincidere.

Il gate state-changing ha due valori effettivi. Se allow_state_changes=true nel config o viene passato
--allow-state-changes, i probe bounded che possono modificare stato sono abilitati; se il valore e' false,
viene passato --no-allow-state-changes oppure il campo e' omesso, la policy effettiva e' false su QUALUNQUE
target, compresi 127.0.0.1, localhost e ::1. Non esiste piu' un'abilitazione automatica per il laboratorio
locale. Nel config il valore del singolo servizio ha precedenza sul valore della sezione execution e il runner
normalizza il valore omesso a false gia' nella costruzione del job, cosi' dry-run, coalescing, report e CLI
vedono la stessa policy. Il flag true non amplia mai scope, autorizzazione DoS/brute-force o protocolli non HTTP;
abilita soltanto le verifiche HTTP state-changing compatibili con lo scope configurato.

La policy viene applicata centralmente ai request contract prima di ZAP/Nuclei e prima
degli specialisti request-level, sia in Deterministic sia nella validazione Agentic e in
--only-tool. Non blocca ogni POST: richieste read-only di query/search/API restano disponibili,
mentre URL distruttivi, metodi DELETE/PUT/PATCH, route/action POST chiaramente mutative, cambio credenziali e upload
vengono esclusi. I body JSON vengono ispezionati ricorsivamente con profondita' bounded, quindi anche una action mutativa annidata non aggira il gate. Controlli benigni come action=view o reset=false restano eleggibili.
I wrapper applicano poi ulteriori policy proprie.

In particolare il gate interessa anche:
  - Dalfox wrapper: il probe aggiuntivo di reflection su richieste POST; i controlli GET e il tool
    Dalfox non vengono globalmente spenti;
  - Browser verifier: il test stored-XSS che inserisce un marker innocuo e ricarica la pagina per
    verificarne la persistenza; i controlli DOM/reflected non persistenti restano disponibili;
  - Workflow verifier: la validazione attiva CSRF tramite POST con/senza token (2), il caricamento di un
    file-marker innocuo e la verifica CAPTCHA tramite rimozione del campo di challenge. Le sole
    osservazioni strutturali dei form possono ancora essere prodotte senza questi invii.

Deterministic e Agentic usano la stessa funzione centrale di orchestratorShared per questa policy:
la selezione del planner AI non puo' aggirare il blocco Python.

Policy tool-specific senza spegnere inutilmente la copertura:
  - Nikto resta attivo con allow_state_changes=false: usa reverse tuning x06, cioe' tutte le classi
    standard tranne File Upload (0) e DoS (6), ed esclude i plugin autonomi put_del_test e auth;
    il baseline autenticato resta controllato dal wrapper, mentre il motore autonomo non riceve cookie
    che potrebbero trasformare una sua GET interna (es. logout) in una modifica di sessione;
  - SQLMap resta detection-only con le tecniche BEUSTQ e non richiede query/write/takeover del target;
  - Commix resta attivo ma, con false, esclude soltanto la tecnica file-based f che scrive output sul filesystem;
  - Nuclei ispeziona strutturalmente i template: mantiene GET/POST dimostrabilmente read-only, ma blocca
    mutazioni non autorizzate; DoS/brute-force e protocolli autonomi headless/javascript/code/network/dns/file/workflow
    restano esclusi indipendentemente da allow_state_changes, e una URL assoluta hardcoded fuori dal target viene rifiutata.

POST realmente trasmessi dopo la discovery:
  - Arjun puo' usare POST quando il request contract selezionato e' POST;
  - ZAP puo' fare replay/seeding e active scan dei request contract POST selezionati;
  - Nuclei usa request contract GET/POST nella fase DAST in tutti i profili: fast mantiene un campione bounded di 10 casi, balanced/deep arrivano a 64/112;
  - SQLMap, Commix, Traversal e il processo Dalfox esterno possono testare un contract POST selezionato;
  - Browser invia il POST stored-XSS soltanto quando allow_state_changes e' abilitato;
  - Workflow puo' fare fino a tre tentativi di autenticazione invalidi su un form POST; CSRF attivo, upload e CAPTCHA
    richiedono invece allow_state_changes=true;
  - Authorization resta GET-only; IDOR usa GET e soltanto POST classificati read-only dal guard centrale, con riferimenti runtime in query/path/JSON/form.
Il logout POST autenticato e' separato: viene riservato alla verifica finale del ciclo di sessione.

DAST request contract: FAST=96, BALANCED=1200, DEEP=3000. I contract vengono eseguiti in batch
sequenziali da 48/160/240 sotto un unico deadline della fase; selected, attempted e completed restano
distinti, quindi un batch parziale o in timeout non viene contato come interamente testato. FAST usa
fuzz aggression low con fuzz-param-frequency 20; BALANCED medium con 100; DEEP high con 1000.
Con allow_state_changes=false i POST read-only restano eleggibili, mentre DELETE/PUT/PATCH, route/action mutative (anche annidate in JSON), cambio credenziali e upload vengono esclusi prima del replay ZAP/Nuclei e prima del ranking/esecuzione degli specialisti request-level, cosi' i casi bloccati non consumano slot che possono essere usati da contract sicuri; per i GET una parola mutativa dentro un normale valore di ricerca/filtro/navigazione (es. q=delete o redirect=/delete-preview) non basta a bloccare il caso, mentre selector di controllo come action/operation/op/task/mode/command/do/event, override espliciti del metodo e query key/path con verbo mutativo restano bloccati; un campo chiamato query non viene considerato GraphQL solo per il nome: servono route/content-type GraphQL o un valore che abbia forma di documento GraphQL, cosi' POST /search e POST /query read-only restano eleggibili; una mutation/subscription GraphQL viene bloccata prima della rete anche se codificata in query= su GET, mentre i body raw application/graphql vengono classificati distinguendo query read-only da operazioni mutative; i documenti multi-operation vengono letti a livello top-level e falliscono chiusi se contengono mutation/subscription, senza confondere nomi di operazione/campo, commenti o stringhe con il tipo di operazione; la stessa verifica vale anche per --only-tool. Il wrapper prova gli
input request-shaped in ordine JSONL Proxify -> YAML MultiDoc Proxify -> lista URL per i soli GET
se entrambi i parser request-shaped falliscono. Non esiste un piccolo limite aggiuntivo al numero
di payload DAST: restano i limiti di request contract, rate/concurrency, template e timeout di profilo.

9. REPORT
---------
Deterministic: .\reports\SecOps_Assessment_<timestamp>.pdf/.html/.json/.review.json
Agentic:       .\reports\SecOps_Agentic_Assessment_<timestamp>.pdf/.html/.json/.review.json

Se l'esecuzione passa da assessmentRunner.py viene creato anche:
  .\reports\Assessment_Results_Data_<ID>.json
Per un singolo report, <ID> coincide ESATTAMENTE con il report_id (per esempio SecOps_Agentic_Assessment_<timestamp>); per assessment multi-job/dry-run coincide con il test_id. Lo schema corrente e' 4 e il file e' autosufficiente per elaborazioni future: oltre a configurazione/job redatti e report_artifacts, incorpora reports_data con summary, coverage per-tool, endpoint_coverage, finding leggibili e grezzi, risultati completi degli scanner, assessment_context, discovery, diagnostics, planner notes/audit, reasoning_summary operativi, action ID e batch del planner, decisioni Agentic, riepilogo dell'analisi AI e rationale/confidence AI per finding. Quando esiste un solo report, assessment_results, assessment_context, discovery, diagnostics, agentic_decisions e ai_analysis sono disponibili anche direttamente al livello principale. Alla fine assessmentRunner.py stampa esplicitamente sia il/i percorso/i PDF sia il percorso Assessment_Results_Data_<ID>.json sotto "Assessment final artifacts".

Il file .review.json e' lo snapshot redatto compatibile con rerenderReport.py; Assessment_Results_Data_<ID>.json incorpora direttamente dati, planner audit e analisi AI per le elaborazioni future. Rigenerazione:
python .\rerenderReport.py --snapshot .\reports\<REPORT>.review.json

Nei finding confermati il report mostra anche conseguenze/danno potenziale e recovery/ripristino.
Deterministic aggiunge una guida conservativa quando il tool non la fornisce; Agentic la produce tramite
l'analisi AI vincolata alle evidenze. Un danno potenziale non viene presentato come danno realmente avvenuto.

Il PDF/HTML/JSON includono inoltre una sezione "Endpoint coverage matrix" nello stesso stile tabellare del resto del report. La matrice deriva dalla discovery finale, dall'eleggibilita' delle azioni del percorso attivo (catalogo Agentic oppure selector Deterministic) e dalle esecuzioni realmente registrate. Per ogni profilo riporta metodo, endpoint/request context scoperto, origine della discovery, tool di sicurezza realmente eseguiti, stato testuale, reason code strutturato e motivazione quando non esiste una prova eseguita. Due POST sullo stesso URL con body/request contract distinti rimangono righe separate tramite un fingerprint non reversibile del contesto body; il body e i valori inviati non vengono riportati nella matrice. I principali reason code sono DEFERRED_LOW_PRIORITY, BUDGET_LIMIT, NO_COMPATIBLE_PARAMETERS, UNSUPPORTED_METHOD, STATE_CHANGE_BLOCKED, OUT_OF_SCOPE, DUPLICATE_ROUTE_VARIANT, HTTP_404 e HTTP_410; nel percorso Agentic PLANNER_DEFERRED distingue i request contract eleggibili che il planner AI non ha selezionato per l'esecuzione. Gli stati restano Tested, Discovered only, Skipped, Execution error, HTTP 404 e HTTP 410: una semplice visita del crawler non viene quindi indicata come test di sicurezza. Prima della matrice viene mostrato un riepilogo numerico con request context scoperti, raggiungibili/in-scope, testati da almeno un'esecuzione concreta, testati da broad/specialist, raggiunti soltanto dal safe-surface sweep, solo discovery, saltati intenzionalmente, errori di esecuzione e 404/410. Sono esposte sia la copertura totale testata sia la copertura broad/specialist, cosi' lo sweep finale non puo' far apparire profonda una copertura ottenuta soltanto con replay sicuri; anonymous e authenticated hanno righe separate e, quando entrambi sono presenti, una riga totale. Nei report multi-entry aggregati la matrice mantiene anche il job/entry point di provenienza. La matrice e endpoint_coverage_summary vengono salvati nel JSON, nello snapshot .review.json e in Assessment_Results_Data_<ID>.json.

NOTE DI VALIDAZIONE RUNTIME
- Un profilo con cookie che la discovery dichiara non autenticato viene escluso dalla pianificazione autenticata; non sopprime la copertura anonima.
- ZAP considera completa la copertura attiva solo se casi pianificati, tentati, avviati e completati coincidono.
- Nikto con processo concluso ma copertura non verificabile viene registrato PARTIAL, non SUCCESS.
- La confidence finale dell'analisi AI viene applicata a tutti i candidate/vulnerability; Chromium puo' imporre un ceiling separato per XSS.
- Le richieste token (1) del provider AI Snap4City hanno timeout HTTP limitati.

I payload di reporting troppo grandi vengono compressi e trasferiti in chunk limitati sullo stesso endpoint MCP/HTTP unificato. Dimensione dei chunk, numero massimo di chunk e limite totale sono coerenti tra client e report server; non viene usato alcun handoff locale su file. Upload e rendering hanno budget distinti; durante la lunga chiamata finale il client stampa heartbeat REPORT WAIT ogni circa 30s e, quando disponibile, l'ultima fase REPORT SERVER, evitando un terminale SSH apparentemente fermo. La matrice endpoint resta completa in HTML/JSON/review, mentre la variante PDF limita per default il dettaglio a 260 righe prioritizzando errori e gap, per evitare che migliaia di righe rallentino inutilmente WeasyPrint. I default sono 120 s per chunk, 900 s per l'upload completo, 4200 s + 60 s/MiB per ricomposizione/rendering con tetto 7200 s e 3600 s per WeasyPrint; sono limiti massimi, non tempi attesi. Il rendering PDF prova in ordine WeasyPrint nativo, immagine Docker di report e Chromium/Playwright, ma SECOPS_REPORT_PDF_TIMEOUT e' un unico budget wall-clock condiviso dall'intera catena: ogni fallback riceve soltanto il tempo rimasto e non riparte con un nuovo timeout completo. Se tutti falliscono o il budget condiviso si esaurisce restituisce un errore controllato con diagnostica senza perdere gli artefatti gia' creati. I limiti possono essere regolati con SECOPS_MCP_REPORT_CHUNK_TIMEOUT, SECOPS_MCP_REPORT_TRANSFER_TIMEOUT, SECOPS_MCP_REPORT_RENDER_TIMEOUT, SECOPS_MCP_REPORT_RENDER_SECONDS_PER_MIB, SECOPS_MCP_REPORT_RENDER_TIMEOUT_MAX e SECOPS_REPORT_PDF_TIMEOUT.

Il report `SecOps_*_Assessment_*` e' il report normale. `SecOps_*_Emergency_*` e' soltanto l'ultima rete di sicurezza: viene creato esclusivamente quando, dopo un errore/timeout del reporting MCP, non e' recuperabile alcun artefatto normale JSON/HTML/review/PDF. Se il report server ha gia' scritto il report normale prima che la risposta HTTP termini, l'orchestratore recupera quei percorsi e non genera un duplicato Emergency. Anche assessmentRunner.py seleziona un solo report primario per job e preferisce sempre il report Assessment a un eventuale Emergency concorrente. Nell'output finale `HTML report (PDF fallback)` indica quindi il normale HTML rimasto disponibile quando manca soltanto il PDF, mentre `Emergency HTML report` indica un vero fallback di ultima istanza.


Diagnostic profile
------------------
Use --mode test when validating a fresh installation or a recent code change. This is a smoke/regression profile, not a security-coverage profile. Every scanner/action deadline is 10 seconds (ZAP, Nuclei, Nikto, FFUF, Session, Arjun, SQLMap, Dalfox, Commix, Traversal, IDOR, Authorization, Browser and Workflow). HTTP/Chromium/service-discovery stages that own an independent wall-clock guard use 8 seconds; the safe-surface sweep uses a short diagnostic guard. Agentic TEST uses one round in the commands printed by initScript.py, at most 32 fairly interleaved planner candidates in one batch, a 24-action reference ceiling (27 only after the normal bounded adaptive request), and AI analysis of at most one finding. The planner control-plane budget is 90 seconds and the analysis budget is 60 seconds; neither enlarges the 10-second scanner deadline. The generic 1200-second MCP default is clamped in TEST: a normal 10-second scanner has about a 90-second outer watchdog, ZAP about 130 seconds, and auxiliary non-report calls stay below 120 seconds. TEST reporting keeps separate 60-second transfer and 180-second PDF-render ceilings; a PDF render timeout returns PARTIAL/time_limit_reached while preserving JSON/HTML/review artifacts. Numeric AI priorities outside 0-100 are clamped and audit-logged; missing/non-numeric/non-finite priority rows are discarded without inventing scores, while explicitly selected IDs are preserved as unranked. Boolean AI/MCP fields are normalized explicitly so the string "false" cannot become True; duplicate action IDs/identical priorities are deduplicated, conflicting priorities remain errors, and malformed scanner metadata is normalized or ignored with diagnostics rather than crashing the run. SQLMap and IDOR-Forge reserve short TEST startup/preflight slices (3s/4s) and classify their exhaustion as time-limited partial results, not dependency failures. FAST/BALANCED/DEEP keep their normal coverage/time budgets unchanged.
