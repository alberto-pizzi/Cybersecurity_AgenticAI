SecOps FastMCP - guida operativa
===============================

START HERE - PERCORSO CONSIGLIATO
=================================
Se stai aprendo il progetto per la prima volta, segui questo ordine.

A) PRIMA INIZIALIZZAZIONE
   Dalla root del repository:
     Windows: python .\initScript.py --with-lab
     Linux/macOS: python3 ./initScript.py --with-lab

   L'initializer verifica dipendenze, scanner, Playwright/Chromium e backend AI.
   Con --with-lab prepara anche DVWA. Al termine stampa comandi gia' pronti.
   Per il primo test conviene usare Deterministic BALANCED sul DVWA locale.
   Dopo la baseline puoi usare Agentic BALANCED.

B) NUOVA APPLICAZIONE - UN SOLO PUNTO DI INGRESSO
   Per un run anonimo o per una sessione di cui possiedi gia' il cookie puoi usare:
     python .\assessmentRunner.py --target https://app.example.org/ --orchestrator deterministic --mode balanced --authorized

   Se hai un cookie autorizzato aggiungi:
     --cookies "<COOKIE_HEADER>"

   IMPORTANTE: la modalita' diretta --target NON accetta username/password del target.
   Non esegue il login OIDC per creare una sessione. Se possiedi soltanto username e
   password del sito devi usare --config con una credenziale di login supportata, per
   esempio kind=snap4city_oidc. In alternativa devi procurarti prima un cookie valido.

   La discovery espande la superficie autorizzata usando HTML, link, form, query string,
   endpoint JavaScript e richieste document/XHR/fetch osservate da Chromium. Origini diverse
   dalla principale entrano solo se dichiarate esplicitamente nello scope autorizzato.

C) NUOVA APPLICAZIONE - CONFIGURAZIONE
   Usa --config quando hai piu' host, porte, base path o identita'. Usalo anche quando
   devi creare la sessione da username/password oppure quando alcuni URL precisi devono
   essere garantiti come punti di ingresso.

   Ogni servizio HTTP/HTTPS puo' essere descritto con service.url completo oppure con
   asset.host/IP, porta, protocollo e base_path.

   In una normale applicazione non serve elencare tutte le pagine interne. Basta la radice
   o il base path e la discovery cerca il resto. Se invece ricevi un elenco di URL che
   devono essere tutti testati e non vuoi dipendere dai link scoperti, inserisci un servizio
   per ciascun URL. configs/tourist-dashboard.json usa questa forma per otto dashboard
   Snap4City sulla stessa origine.

   Prima di avviare gli scanner esegui un dry-run:
     python .\assessmentRunner.py --config .\configs\platform.example.json --orchestrator deterministic --mode balanced --dry-run

D) AUTENTICAZIONE DA CONFIG
   Una credenziale kind=snap4city_oidc puo' usare un cookie gia' disponibile oppure
   username/password del target. Il runner trasforma il login riuscito in una sessione cookie
   e passa quella sessione agli orchestrator esistenti.

   Se optional=true e il login non e' disponibile o fallisce, il job continua in anonimo.
   Se usi --auth-only, invece, la sessione autenticata e' obbligatoria e il job viene bloccato
   quando il login non riesce.

E) QUALE MODALITA' CONVIENE
   fast      = smoke test o diagnostica breve
   balanced  = scelta consigliata per il normale assessment
   deep      = copertura e budget maggiori. Usarla dopo aver verificato target, login e scope

   Deterministic = prima baseline consigliata. L'ordine e' fisso e riproducibile.
   Agentic       = planner AI e analisi AI finale delle evidenze.
   assessmentRunner.py = percorso consigliato per l'uso normale e per i config.
   orchestrator*.py diretto = utile soprattutto per target singoli e diagnostica manuale.

F) COME VEDERE COSA STA FACENDO
   Durante il run il terminale mostra fase, tool, target, stato, limiti e diagnostica.
   Deterministic segue la pipeline fissa. Agentic mostra anche i round e le azioni scelte.
   PARTIAL, time_limit, skipped ed error descrivono l'esecuzione o la copertura. Non indicano
   automaticamente la presenza o l'assenza di una vulnerabilita'.

   Dopo un run con assessmentRunner.py il riferimento piu' completo e':
     .\reports\Assessment_Results_Data_<ID>.json

   Contiene risultati scanner, coverage, discovery, diagnostics, finding, contesto,
   planner audit, decisioni Agentic e analisi AI quando presenti.

G) DOVE SONO I RISULTATI
   .\reports\SecOps_*.pdf          -> report leggibile
   .\reports\SecOps_*.html         -> report navigabile
   .\reports\SecOps_*.json         -> dati tecnici del report
   .\reports\SecOps_*.review.json  -> snapshot redatto per rerenderReport.py
   .\reports\Assessment_Results_Data_<ID>.json -> dataset redatto autosufficiente del runner

   assessmentRunner.py stampa i percorsi esatti alla fine sotto "Assessment final artifacts".

Per tutti i test usa esclusivamente target autorizzati. Su target non locali mantieni
allow_state_changes=false o --no-allow-state-changes salvo autorizzazione esplicita alle
verifiche state-changing. Il gate e' vincolante per i percorsi che lo supportano. Non e'
un interruttore universale per tutti gli scanner esterni.

AMBIENTE
--------
Apri il terminale nella radice del progetto:
  Set-Location "<PROJECT_ROOT>"

Usa soltanto target tuoi o esplicitamente autorizzati. Per un target remoto
aggiungi --authorized e mantieni il Cookie header tra virgolette.

MCP
---
Un solo server FastMCP (`servers/secopsServer.py`) espone l'intero catalogo su
http://127.0.0.1:8100/mcp. I moduli dei singoli tool sono importati come componenti e
non aprono listener propri. Deterministic e Agentic condividono endpoint, registry, selector
e contratti MCP. Non sono previsti trasporti MCP alternativi.

0. LEGENDA TOKEN/CREDENZIALI
----------------------------------
In questo documento la parola "token" indica due concetti di accesso diversi e senza
relazione tra loro. Ogni menzione successiva di "token" in questo file e' etichettata con
uno dei due marcatori qui sotto, cosi' e' sempre chiaro a quale accesso ci si riferisce:
  (1) TOKEN-AI: token di accesso all'LLM Snap4City (access/refresh). Autenticano l'API LLM
      remota, cioe' il backend AI usato dal planner Agentic. Gestiti dal TokenManager
      Snap4City e salvati in token_stored.json; non hanno nulla a che vedere con il target
      da testare.
  (2) TOKEN-TARGET: token di accesso alla piattaforma da verificare (cookie/JWT/token CSRF
      del target, es. --cookies, --jwt-token, login dashboard_session). Appartengono alla
      piattaforma sottoposta ad assessment. Non sono mai credenziali Snap4City e non
      vengono condivisi con il provider AI.

1. INIZIALIZZAZIONE
------------------
Preparazione completa consigliata (default AI = tutti e tre):
python .\initScript.py --with-lab

Se NON specifichi ne' --prepare-ai ne' --agentic-model, --with-lab prepara:
  - Ollama + llama3.1:8b
  - Ollama + qwen2.5:7b

Snap4City e' remoto: non viene scaricato; l'initializer autentica e verifica che l'endpoint risponda.
Se la preparazione Snap4City fallisce per endpoint/modello non raggiungibile, l'errore viene mostrato ma
l'inizializzazione prosegue. Se disponibile viene scelto un modello Ollama locale verificato; altrimenti

Preparare un solo backend/model:
python .\initScript.py --with-lab --prepare-ai snap4city
python .\initScript.py --with-lab --prepare-ai llama
python .\initScript.py --with-lab --prepare-ai qwen

Se specifichi --agentic-model SENZA --prepare-ai, l'initializer prepara automaticamente solo quel modello:
python .\initScript.py --with-lab --agentic-model llama
python .\initScript.py --with-lab --agentic-model qwen --run agentic --mode balanced
python .\initScript.py --with-lab --agentic-model snap4city --run agentic --mode balanced

Se specifichi ENTRAMBI, devono essere coerenti:
  OK:    --prepare-ai all --agentic-model qwen
  OK:    --prepare-ai qwen --agentic-model qwen
  ERRORE: --prepare-ai llama --agentic-model qwen

Nel repository e' presente configs/dvwa.example.json come placeholder leggibile senza una sessione valida.
Con --with-lab viene creato anche configs/dvwa.generated.json usando la sessione DVWA appena
generata. Il file e' gia' pronto per assessmentRunner.py; contiene una credenziale locale temporanea
e non va riutilizzato come file di configurazione condiviso.

Eseguire subito l'assessment generato dopo l'init:
python .\initScript.py --with-lab --run deterministic --mode balanced
python .\initScript.py --with-lab --run agentic --mode balanced
python .\initScript.py --with-lab --prepare-ai qwen --run agentic --mode balanced

Alla fine l'initializer stampa i comandi DVWA assessmentRunner FAST/BALANCED/DEEP e il comando diretto
orchestratorAgentic.py. Inoltre scorre automaticamente configs/*.json e, per ogni configurazione reale, stampa
un comando Deterministic BALANCED e un comando Agentic BALANCED. Sono esclusi i file di esempio/template
(il nome contiene example, sample o template) e dvwa.generated.json, gia' coperto dai comandi DVWA.
La stessa lista dinamica viene stampata anche con --commands-only. I comandi manuali degli orchestrator restano validi.

Il modello/provider AI Snap4City usa snap4city_model_credentials.json. Questo file NON contiene le credenziali della dashboard target.
Se contiene ancora placeholder o manca e il terminale e' interattivo, username/password del provider AI vengono richiesti in console; la password non viene mostrata.

python .\initScript.py --commands-only

Le dipendenze upstream di IDOR-Forge restano nella .venv del repository.

2. ASSESSMENT RUNNER E CONFIGURAZIONE
------------------------------------
assessmentRunner.py puo' leggere una piattaforma da JSON oppure ricevere direttamente --target e --cookies,
quindi delega ogni servizio HTTP/HTTPS agli orchestrator esistenti. Non sostituisce Deterministic o Agentic.
Protocolli non web possono restare nell'inventario ma vengono registrati come non supportati e non testati.

DVWA generato dall'initializer:
python .\assessmentRunner.py --config .\configs\dvwa.generated.json --orchestrator deterministic --mode balanced --dry-run
python .\assessmentRunner.py --config .\configs\dvwa.generated.json --orchestrator deterministic --mode balanced
python .\assessmentRunner.py --config .\configs\dvwa.generated.json --orchestrator deterministic --mode balanced --auth-only
python .\assessmentRunner.py --config .\configs\dvwa.generated.json --orchestrator agentic --model snap4city --max-rounds 2 --mode balanced --require-ai

Il file DVWA generato contiene il cookie ma ha auth_only=false: senza --auth-only vengono eseguiti
sia il profilo anonimo sia quello autenticato. Con --auth-only viene eseguito soltanto l'autenticato.

Modalita' diretta senza file JSON:
python .\assessmentRunner.py --target http://127.0.0.1 --cookies "PHPSESSID=<SESSION>; security=low" --orchestrator deterministic --mode balanced
python .\assessmentRunner.py --target http://127.0.0.1 --cookies "PHPSESSID=<SESSION>; security=low" --orchestrator deterministic --mode balanced --auth-only
python .\assessmentRunner.py --target http://127.0.0.1 --orchestrator deterministic --mode balanced
python .\assessmentRunner.py --target http://127.0.0.1 --cookies "PHPSESSID=<SESSION>; security=low" --orchestrator agentic --model snap4city --max-rounds 2 --mode balanced --require-ai

In modalita' diretta, un cookie senza --auth-only abilita anonimo + autenticato.
Con --auth-only viene eseguito solo il profilo autenticato. Senza cookie il run e' anonimo.
--config e --target sono alternativi.
La modalita' --target non accetta username/password del target e non esegue il login OIDC.
Se hai soltanto username/password usa un config con una credenziale supportata, per esempio
kind=snap4city_oidc, oppure ottieni prima un cookie autorizzato.

Override disponibili senza modificare il JSON:
  --orchestrator deterministic|agentic
  --mode fast|balanced|deep
  --model snap4city|llama|qwen
  --max-rounds 1|2|3
  --auth-only
  --require-ai / --no-require-ai
  --authorized
  --authorized-origin https://api.example.org      (ripetibile)
  --authorized-host-suffix example.org            (ripetibile)
  --allow-state-changes
  --no-allow-state-changes
  --dry-run
  --only <ASSET/SERVICE>

Per llama/qwen il runner verifica il modello esatto gia' installato in Ollama. Non lo scarica e non
accetta la sostituzione silenziosa con l'altro modello: inizializza prima il modello richiesto.

Configurazioni target: URL completo oppure host/IP + porta
--------------------------------------------------------
Per un servizio HTTP/HTTPS il config accetta due forme equivalenti:
  1) link completo nel campo service.url, per esempio:
       "url": "https://turismo.example.org/dashboard"
  2) asset.host + service.port; protocol e base_path restano opzionali secondo il caso.
     Se protocol non e' indicato, la porta 443 implica https, le altre porte implicano http.
     Per HTTPS su porte non standard conviene indicare esplicitamente "protocol": "https".

Il campo service.url, quando valorizzato, ha precedenza su host/port/base_path. I config esistenti
che usano host + protocol + port continuano a funzionare senza modifiche.

configs/tourist-dashboard.json contiene gia' gli otto URL HTTPS pubblici forniti per la dashboard turistica.
Ogni URL resta un servizio separato per garantire che tutti gli entry point vengano analizzati, ma il config e'
anonymous-only: non contiene credential_ref e quindi assessmentRunner.py non chiede username/password del target.
allow_state_changes resta false per tutti gli otto servizi.

Poiche' gli otto URL appartengono allo stesso target logico, il blocco reporting usa aggregate_report=true.
Se un entry point termina con error o blocked prima di produrre il proprio report, resta comunque visibile nel report aggregato come limitazione di esecuzione; anche un job concluso con successo ma privo di un artefatto per-entry leggibile viene marcato come limitazione partial.
aggregate_report e keep_job_reports devono essere booleani JSON reali (true/false); stringhe come "false" vengono rifiutate dalla validazione del config.
Dopo l'esecuzione dei job viene prodotto un solo report primario che aggrega risultati, coverage e discovery.
Con keep_job_reports=false gli artefatti dei singoli entry point vengono spostati in
reports/supporting/<assessment-id>/ come evidenza tecnica di supporto; i job restano comunque distinti e ciascuno
mantiene i propri scanner e budget.
Nel report aggregato ogni finding conserva la provenienza: sono mostrati il tool/scanner, l'URL interessato e
l'entry point/job da cui deriva l'evidenza. Se finding equivalenti vengono deduplicati, la voce finale mantiene
tutti gli entry point e i job che l'hanno corroborata.


Dry-run consigliato:
  python .\assessmentRunner.py --config .\configs\tourist-dashboard.json --orchestrator deterministic --mode balanced --dry-run --authorized

Esempio architettura complessa:
  configs/platform.example.json
Mostra esplicitamente entrambe le forme supportate: un servizio con service.url completo e altri servizi con asset.host/IP + porta/protocol/base_path. Include inoltre due identita' web, SSH/22 mantenuto solo come inventario e il blocco reporting con aggregate_report=true e keep_job_reports=false, cosi' i job HTTP/HTTPS della stessa piattaforma logica confluiscono in un unico report primario.

4. AGENTIC
----------
Modelli Agentic supportati (il provider viene scelto internamente):
  snap4city  -> Snap4City, endpoint llama4-agentic-inference
  llama      -> Ollama locale, llama3.1:8b
  qwen       -> Ollama locale, qwen2.5:7b

Llama e Qwen condividono la stessa verifica Ollama, ma la selezione del modello e' esatta:
qwen non viene sostituito automaticamente da llama e llama non viene sostituito da qwen.

Non esiste un'opzione --ai-provider: --model sceglie l'AI e il codice deduce automaticamente
il provider corretto. Quindi snap4city usa Snap4City; llama e qwen usano Ollama.

I comandi assessment Agentic stampati da initScript.py usano Snap4City per default e --require-ai quando Snap4City e' verificato; viene inoltre stampato un comando diretto orchestratorAgentic.py con il backend effettivamente disponibile.

Snap4City FAST (2 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 2 --mode fast --require-ai

Snap4City BALANCED (2 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 2 --mode balanced --require-ai

Snap4City DEEP (3 round):
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model snap4city --max-rounds 3 --mode deep --require-ai

Alternative locali Ollama:
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model llama --max-rounds 2 --mode balanced --require-ai
python .\orchestratorAgentic.py --target <TARGET> --cookies "<COOKIE_HEADER>" --auth-only --authorized --model qwen --max-rounds 2 --mode balanced --require-ai

Con seconda identità:
python .\orchestratorAgentic.py --target <TARGET> --cookies "<PRIMARY_COOKIE>" --secondary-cookies "<SECOND_ACCOUNT_COOKIE>" --auth-only --authorized --model snap4city --max-rounds 3 --mode deep --require-ai

Snap4City rispetta la priorita' del TokenManager Snap4City (1): prima riusa un access token (1) ancora valido in token_stored.json;
se e' scaduto prova il refresh token (1); con credenziali reali in snap4city_model_credentials.json usa username/password come ultimo passo normale.
Se snap4city_model_credentials.json manca o contiene ancora placeholder, i placeholder non vengono mai inviati: vengono provati prima access token (1)
e refresh token (1) gia' salvati e solo se entrambi non sono utilizzabili, con terminale interattivo, vengono chiesti username/password
per quel processo. La password viene letta senza echo e le credenziali inserite non vengono scritte automaticamente nel JSON.

Senza --require-ai, se il planner AI fallisce può essere usato il piccolo fallback deterministico discovery-derived (massimo
3 azioni sicure per round). Con --require-ai il fallback del planner è disabilitato e il run fallisce se planning/analysis AI
non completano correttamente. Durante un assessment gia' avviato un fallimento del backend AI non cambia automaticamente
provider o modello: Snap4City, Llama e Qwen restano selezioni distinte. Il fallback Snap4City -> Ollama descritto nella sezione
di inizializzazione avviene soltanto durante la preparazione, prima di avviare l'assessment.

Il planner riceve candidati derivati dalla discovery e li seleziona in base al
valore informativo atteso. Può differire controlli ridondanti e non usa una
checklist minima. Ogni azione passa dagli stessi validator del Deterministic. Al termine, un nodo AI separato
rivaluta severity, descrizione, impatto, conseguenze potenziali, azioni di recovery/ripristino e remediation
dei finding usando soltanto l’evidenza degli scanner; categoria, verification status ed evidenza non possono
essere modificati. Se il tool aveva gia' fornito questi testi, l'originale resta nel riquadro di audit del report.

DISCOVERY E COPERTURA DINAMICA
-----------------------------
Per default initScript.py installa Playwright Chromium, su Linux richiede anche le dipendenze host
con `python -m playwright install --with-deps chromium` e verifica un avvio headless reale. Se questa
verifica fallisce, l'inizializzazione fallisce invece di lasciare il Browser verifier in stato
`missing_playwright_browser`. Solo `--skip-browser` disattiva esplicitamente questa garanzia.

La discovery combina crawler HTTP, form/query, endpoint letterali trovati negli script e una sola coda
dinamica Chromium. Il browser parte dalle pagine HTML sicure e piu' interessanti gia' note, le carica e
osserva richieste document/XHR/fetch nell'ambito autorizzato; origini diverse dalla principale entrano solo se dichiarate con allowed_origins/allowed_host_suffixes o con i corrispondenti flag CLI. I nuovi link/documenti autorizzati vengono reinseriti nella stessa coda. I budget Chromium sono adattivi per profilo: 16/32, 60/120 e 120/240 (base/massimo) in fast/balanced/deep; l'overflow oltre la base viene usato solo se restano pagine dinamiche con punteggio almeno pari al 75% del cutoff della base. I budget del crawler HTTP restano 35/90/180; il log segnala separatamente quando viene saturato il budget di pagine utili o quello dei tentativi mentre esistono ancora candidati rimasti in coda; l'origine primaria riceve un piccolo bonus generico nel ranking della coda, così le sibling origin esplicitamente autorizzate restano esplorabili senza sottrarre facilmente le pagine più rilevanti al target principale; le XHR/fetch osservate non consumano un ulteriore budget di pagine e possono generare
request contract. Per le richieste realmente inviate vengono registrati anche status/content-type della response
o requestfailed, cosi' il planner distingue endpoint raggiunti da 404/410 senza scartare 401/403. Le risposte HTTP 404/410 restano nei warning e nel report, ma non consumano il budget di pagine utili del crawler e non diventano seed HTML per Chromium/ZAP. Un limite separato di tentativi HTTP, pari a 1,5 volte il budget utile, evita che grandi insiemi di link morti causino richieste non bounded. Se esistono pagine HTML ma Chromium conclude con 0 navigazioni, la console mostra un BROWSER WARNING e porta gli errori Playwright/runtime/navigation prima dei normali 404/410. Nel Deterministic la discovery Playwright sincrona viene eseguita in un worker thread, evitando l'uso della Sync API dentro l'event loop asyncio di LangGraph. Se il numero di navigazioni raggiunge il limite del profilo, la console stampa inoltre la saturazione usato/budget. Le richieste
browser non-GET e le rotte distruttive vengono intercettate prima dell'invio:
il body puo' diventare request contract con metodo e parametri reali; GET/POST vengono poi consumati dai tool
compatibili, mentre gli altri metodi restano tracciati come superficie osservata.
POST e JSON restano request contract di prima classe: non vengono eliminati per rendere la discovery sicura.
La coda deduplica per origin+path+nomi parametri, applica quote per origin e penalizza asset statici, vendor/chunk,
paginazioni/archivi e varianti equivalenti; API, form, XHR/fetch e superfici con parametri ricevono priorita'.
Le origini sorelle autorizzate possono essere sottoposte a ZAP/Nuclei/Nikto come target separati, ma la copertura broad e' ordinata per rilevanza per evitare che fast/balanced spendano gran parte del tempo su host secondari. Il ranking per origine usa route applicative, form, request contract, navigazioni/reti browser e parametri realmente osservati; il broad sweep completo usa una quota adattiva: 1/3/8 sibling origin base in fast/balanced/deep, con overflow fino a 2/5/12 soltanto per origini aggiuntive con punteggio almeno pari al 75% del cutoff base e con evidenza applicativa interattiva osservata. I timeout delle broad sibling run sono ridotti rispettivamente al 50%/60%/75% del timeout broad del target principale, con minimo 45s. Questi limiti riguardano solo ZAP/Nuclei/Nikto broad: gli specialisti continuano a poter scegliere request contract ad alto valore su qualunque sibling origin osservata e autorizzata. Quando anonymous e authenticated sono entrambi presenti, la stessa broad scan senza cookie viene eseguita una sola volta sotto anonymous. Il cookie della
origine principale non viene inoltrato automaticamente a host diversi; i probe di sessione restano exact-origin.
Deterministic esegue la discovery Playwright sincrona in worker thread quando il nodo LangGraph e' dentro asyncio. Agentic usa inoltre discover_target_sync_safe(): il percorso CLI normale e' sincrono, ma se la stessa discovery viene riusata dentro un event loop viene spostata automaticamente in un worker prima di entrare nella Playwright Sync API.

ZAP: fast=targeted, balanced=prioritized, deep=full bounded; la modalita' passiva resta per i soli
controlli diagnostici. L'inventario active usa API Python/JSON e fallback curato; ogni scanner ID viene
abilitato separatamente e il log distingue piano teorico da regole accettate. Le risorse statiche non possono
essere scelte come target active. I request contract parametrizzati restano il piano preferito; se su un'origine
non esiste alcun contract parametrizzato compatibile, ZAP prova comunque un fallback active bounded su massimo
1/2/3 pagine GET applicative sicure in fast/balanced/deep, recurse=false, usando una piccola unione di regole
installate per reflected-XSS, SQL injection generica, traversal e command injection. Non viene quindi avviato uno
spider active ricorsivo dell'intero dominio. PARTIAL/no_active_scan_rules_enabled resta solo quando non esiste
ne' un piano parametrizzato compatibile ne' una pagina GET sicura con almeno una regola curata effettivamente
abilitabile. Le observation passive conservate sono 60/220/450 in fast/balanced/deep; i security finding non
sono soggetti a questo tetto di observation. Richieste equivalenti con stesso metodo, path e parametri restano deduplicate.
Nuclei: balanced e deep possono usare request contract per DAST gap checks bounded. Il DAST prova prima
l'input Proxify JSONL; se il runtime Nuclei lo rifiuta, gli stessi contract GET/POST vengono ritentati
in YAML MultiDoc Proxify. Solo se entrambi i formati request-shaped falliscono si usa la lista URL per i GET compatibili;
i POST non rappresentabili restano esplicitamente non coperti invece di essere dichiarati testati.
Prima del prompt Agentic, Python costruisce e valida tutte le azioni concrete discovery-derived, poi le raggruppa per coppia (profilo, tool). Il modello NON sceglie i singoli URL di SQLMap/ZAP/Browser: sceglie capability group come anonymous/sqlmap o authenticated/zap; Python espande ogni gruppo scelto nei request contract esatti usando ranking deterministico, compatibilita' e budget adattivi. L'espansione ruota tra i tool scelti dello stesso profilo, quindi un gruppo con molti URL non puo' consumare tutto il budget prima degli altri tool selezionati.

I budget Agentic sono separati per profilo. In fast/balanced/deep ogni profilo attivo dispone rispettivamente di 12/16/18 tool group. FFUF, ZAP, Nuclei, Session, Nikto e JWT, quando eleggibile, sono baseline deterministiche e non dipendono dalla scelta del modello. Le azioni concrete sono anch'esse per profilo e per round: base 48/144/288 con tetto adattivo 80/240/480. I tetti massimi superano la somma degli attuali limiti per-tool 65/214/463, quindi normalmente il limite globale non tronca casi gia' ammessi dai singoli tool; resta un guardrail di emergenza. Python usa la capacita' oltre il base soltanto quando i gruppi selezionati contengono ancora azioni concrete distinte gia' validate; l'AI non modifica il tetto. Con anonymous+authenticated le quote restano indipendenti. Una azione concreta e' una invocazione scanner/request contract, non un singolo campo: piu' parametri dello stesso request contract possono essere testati nella stessa azione. Nella identita' Agentic entrano anche i nomi dei parametri/file/token/campi, evitando che due contratti con set di input diversi vengano collassati solo perche' hanno lo stesso URL/metodo. Le azioni gia' generate e validate ma non entrate nel tetto del round rimangono eleggibili nel round successivo; i limiti separati dei singoli specialisti continuano a delimitare quanti request contract entrano nel pool.
Il catalogo compatto mostrato all'AI contiene al massimo 32/40/48 tool group complessivi ed e' costruito equamente tra i profili. La breadth review e' anch'essa per profilo: valuta la scarsita' sulle sole capability non-baseline e puo' aggiungere al massimo 3/6/8 tool group, senza superare il tetto totale 12/16/18 di quel profilo. La console separa concrete_pool, group_pool/tool_groups, baseline_groups, ai_groups, review_groups e concrete_actions e mostra base, tetto adattivo e numero di azioni rinviate per ogni profilo. Le scansioni broad su sibling origin non vengono duplicate sotto authenticated quando anonymous e' disponibile, perche' su tali origini il cookie del target principale viene comunque rimosso. Inoltre il pool broad delle sibling usa il ranking condiviso con base 1/3/8 e massimo adattivo 2/5/12 in fast/balanced/deep; gli specialisti non ereditano questo cap e restano liberi di usare i loro request contract autorizzati.
Le policy che non dipendono dal planner sono comuni a Deterministic e Agentic e vengono applicate a ogni profilo: scope/cookie isolation, gestione 404/410, limiti Chromium, ranking e overflow specialisti, fallback active ZAP, input Nuclei e verifica XSS finale. Anche la verifica XSS finale Chromium usa base/max 8/12, 40/64 e 120/180 candidati PER PROFILO, quindi anonymous non puo' consumare la quota authenticated. I budget tool-group/azioni restano invece specifici dell'Agentic: il Deterministic non ha un tetto globale del planner e percorre direttamente i casi selezionati per ciascun tool e profilo.
JWT e' analizzato per profilo su massimo 16/64/192 token unici scoperti in fast/balanced/deep. Il controllo e' economico e locale, per questo il limite e' molto piu' ampio; in Agentic la capability JWT e' baseline quando esistono token. I valori raw restano input locali del verifier e non vengono mostrati nel catalogo compatto del planner AI.
Gli specialisti sui parametri privilegiano API/dati, identificatori/query, POST/JSON e richieste
osservate dal browser rispetto a parametri puramente di navigazione. Il routing e' distinto per profilo:
login/SSO/OIDC/identity-provider restano superficie testabile nel profilo anonimo, mentre nel profilo autenticato
non vengono inviati a SQLMap/Dalfox/Commix/Traversal. Logout/signout/logoff segue la regola opposta: l'anonimo
lo ignora; l'autenticato ne conserva il request contract GET/POST senza eseguirlo durante discovery/scanner e lo
riserva al controllo finale di lifecycle della sessione.
Entrambi gli orchestratori eseguono infine una verifica Chromium candidate-driven sugli XSS ancora non confermati.
Il budget e' separato per profilo e adattivo: base 8/40/120 e massimo 12/64/180 in fast/balanced/deep. L'overflow
si apre soltanto quando il base e' saturo e i candidate rinviati restano almeno al 75% del punteggio di cutoff;
il punteggio deterministico considera corrispondenza del contesto/parametro, evidenza client-side, traffico browser
osservato e prova scanner disponibile. Il browser riceve solo il parametro del finding sorgente e seleziona il request
contract piu' vicino anche in base agli altri parametri del contesto, cosi' candidate sullo stesso path/parametro ma
con linkUrl/pageTitle/linkId differenti vengono verificati separatamente. L'AI non decide l'overflow finale XSS. Esecuzione
del marker => vulnerability con confidence high; reflection senza esecuzione => candidate con severity invariata e
confidence al massimo medium; nessuna riproduzione nel controllo bounded => severity invariata e confidence low.
La severity rappresenta l'impatto potenziale se il finding fosse reale, mentre la confidence rappresenta la forza
dell'evidenza raccolta. L'analisi AI successiva puo' arricchire la descrizione e rivalutare la severity in base
all'impatto, ma non puo' superare il tetto di confidence deterministico del browser: MEDIUM per reflection non
eseguita e LOW per mancata riproduzione bounded. CSS, JavaScript standalone, immagini e font non sono candidati Browser-XSS. Nel Deterministic il passaggio avviene dopo i controlli speciali e prima del report e
non ripete un URL/metodo/parametro gia' verificato con successo nella precedente fase browser/workflow. Nell'Agentic
avviene prima dell'analisi AI e del report.
Dopo gli altri controlli autenticati, il session verifier puo' eseguire un logout scoperto in modo bounded e poi
riusare il cookie precedente sulla pagina protetta: se il vecchio cookie mantiene accesso autenticato viene prodotto
un finding vulnerability confermato (CWE-613); se viene rifiutato l'invalidazione e' verificata; se l'esito non e'
distinguibile il controllo resta PARTIAL. Il logout non viene quindi fuzzato genericamente e non puo' interrompere
gli scanner autenticati precedenti.
Gli URL molto lunghi vengono compattati solo nella stampa terminale (endpoint + numero parametri/lunghezza query); URL completi, request contract ed evidenze restano invariati nei risultati JSON e nei report. La soglia e' configurabile con SECOPS_TERMINAL_URL_MAX.

Prima del taglio base/adattivo, i selettori request-oriented limitano inoltre a 2/3/4 in fast/balanced/deep le varianti che hanno stessa origine, path, metodo e stessi nomi dei parametri ma cambiano soltanto i valori. Cosi' /user?id=1, /user?id=2, ... non saturano da soli il budget di SQLMap/IDOR/Authorization; route o set di campi realmente diversi restano indipendenti. La regola e' generica e comune a Deterministic e Agentic.

Budget adattivo specialisti: i valori base/max indicano il limite fisso e il tetto massimo raggiungibile.
La priorita' non e' decisa dal modello AI: orchestratorShared.py assegna deterministicamente il punteggio
in base alla classe dello specialista e all'evidenza del request contract. L'overflow si attiva solo se il
budget base e' saturo; un caso rinviato deve avere almeno il 75% del punteggio del caso che chiude il budget
base e deve contenere almeno un segnale specifico della classe (parametro/route pertinente, riferimento
numerico IDOR, segnale identita/risorsa Authorization, source/sink browser o segnale form/workflow). POST/JSON, XHR/fetch osservato, risposta 2xx/3xx e route applicative
rafforzano la priorita' ma non concedono overflow da soli. L'AI Agentic puo'
scegliere tra le azioni rese eleggibili, ma non puo' cambiare punteggi, soglia, scope o tetto adattivo.
IDOR e Authorization usano lo stesso schema adattivo degli altri specialisti. I timeout per singolo run non aumentano con l'overflow.

Chi decide il ranking: non esiste un servizio o modello separato. La discovery costruisce i request contract;
poi funzioni Python in orchestratorShared.py assegnano punteggi diversi per ciascun tool.
  - _tool_case_priority(): SQLMap, Dalfox, Commix, Traversal e IDOR;
  - _browser_case_priority(): Browser/XSS;
  - _workflow_case_priority(): workflow POST, upload, auth, CAPTCHA e token/CSRF;
  - _authorization_case_priority(): controlli read-only su identita', oggetti e risorse privilegiate;
  - Arjun usa un ranking endpoint dedicato.
Il punteggio parte da piccoli pesi generici su path/nomi parametri e viene dominato dai segnali della classe:
SQL/data e parametri SQL per SQLMap, input XSS e traffico browser per Dalfox/Browser, cmd/host per Commix,
file/path/download per Traversal, riferimenti numerici per IDOR, campi/route identita-risorsa per Authorization,
form upload/auth/CAPTCHA/token per Workflow. POST, JSON, XHR/fetch e risposta live 2xx/3xx rafforzano il punteggio.
Prima dell'ordinamento vengono esclusi i casi incompatibili o non sicuri; 404/410 osservati sono fortemente
penalizzati, le varianti equivalenti vengono deduplicate e solo dopo si applicano base e overflow adattivo.
Deterministic usa direttamente questa classifica. Agentic riceve lo stesso pool gia' classificato, lo raggruppa
per profilo/tool e lascia all'AI la scelta della capability, non la classifica dei singoli URL.

ZAP e Nuclei possono generare molte richieste per ciascun caso/target selezionato. I casi Nuclei
DAST sono scelti dal wrapper Python in modo deterministico usando metodo, path, parametri/body,
content-type, evidenza API/XHR/fetch e response Chromium; Nell'Agentic Nuclei fa parte della baseline deterministica quando eleggibile; il planner AI non decide i singoli request contract DAST. Per microX, se il login automatico o DASHBOARD_TEST_COOKIE
producono una sessione valida, gli stessi budget si applicano anche al profilo authenticated; altrimenti
restano applicati al solo profilo anonimo.

      --skip-scanners --skip-preflight --skip-browser --require-browser --commands-only

--prepare-ai: all, snap4city, llama, qwen.
Se --prepare-ai e --agentic-model sono entrambi omessi, il valore effettivo e' all.
Se --prepare-ai e' omesso ma --agentic-model e' presente, il valore effettivo di preparazione diventa quel modello.
Con --with-lab e valore all vengono predisposti entrambi i modelli Ollama e verificato Snap4City.
Con snap4city l'initializer non provisiona ne' richiede Ollama se nessun modello locale e' richiesto.
Se --prepare-ai e --agentic-model sono entrambi presenti, all include qualunque modello; una selezione singola deve invece coincidere.

Il gate state-changing usa tre stati. Se allow_state_changes=true nel config o viene passato
--allow-state-changes, i probe bounded sono abilitati; se allow_state_changes=false oppure viene
passato --no-allow-state-changes, sono disabilitati anche su un laboratorio locale. Soltanto se
il valore non e' specificato viene applicato il default automatico: 127.0.0.1, localhost e ::1
abilitano i probe, mentre qualunque altro host, compresi indirizzi privati/LAN come
dashboard-test / 192.168.1.81, li mantiene disabilitati. Nel config il valore del singolo servizio
ha precedenza sul valore della sezione execution. Questi flag non abilitano rotte distruttive e
non disabilitano l'intero scanner: limitano solo le verifiche attive che possono cambiare stato.

Il flag non e' un interruttore universale no-write per tutti gli scanner: viene passato
specificamente ai percorsi sotto. SQLMap, Commix, ZAP, Nuclei e gli altri wrapper
non leggono questo flag e mantengono le rispettive policy/bounds indipendenti.

In particolare il gate interessa:
  - Dalfox wrapper: il probe aggiuntivo di reflection su richieste POST; i controlli GET e il tool
    Dalfox non vengono globalmente spenti;
  - Browser verifier: il test stored-XSS che inserisce un marker innocuo e ricarica la pagina per
    verificarne la persistenza; i controlli DOM/reflected non persistenti restano disponibili;
  - Workflow verifier: la validazione attiva CSRF tramite POST con/senza token (2), il caricamento di un
    file-marker innocuo e la verifica CAPTCHA tramite rimozione del campo di challenge. Le sole
    osservazioni strutturali dei form possono ancora essere prodotte senza questi invii.

Deterministic e Agentic usano la stessa funzione centrale di orchestratorShared per questa policy:
la selezione del planner AI non puo' aggirare il blocco Python.

POST realmente trasmessi dopo la discovery:
  - Arjun puo' usare POST quando il request contract selezionato e' POST;
  - ZAP puo' fare replay/seeding e active scan dei request contract POST selezionati;
  - Nuclei usa i request contract POST nella fase DAST di balanced/deep (DAST e' disabilitato in fast);
  - SQLMap, Commix, Traversal e il processo Dalfox esterno possono testare un contract POST selezionato;
  - Browser invia il POST stored-XSS soltanto quando allow_state_changes e' abilitato;
  - Workflow puo' fare fino a tre tentativi di autenticazione invalidi su un form POST; CSRF attivo, upload e CAPTCHA
    richiedono invece allow_state_changes=true;
  - IDOR-Forge e Authorization restano GET-only.
Il logout POST autenticato e' separato: viene riservato alla verifica finale del ciclo di sessione.

Il PDF/HTML/JSON include inoltre una sezione "Endpoint coverage matrix" nello stesso stile tabellare del resto del report. Per ogni profilo riporta metodo, endpoint/request context scoperto, origine della discovery, tool di sicurezza realmente eseguiti, stato testuale, reason code strutturato e motivazione quando non esiste una prova eseguita. I principali reason code sono DEFERRED_LOW_PRIORITY, BUDGET_LIMIT, NO_COMPATIBLE_PARAMETERS, UNSUPPORTED_METHOD, STATE_CHANGE_BLOCKED, OUT_OF_SCOPE, DUPLICATE_ROUTE_VARIANT, HTTP_404 e HTTP_410; nel percorso Agentic PLANNER_DEFERRED distingue i request contract resi eleggibili dal ranking deterministico ma non eseguiti dopo la pianificazione dei tool-group. Gli stati restano Tested, Discovered only, Skipped, Execution error, HTTP 404 e HTTP 410: una semplice visita del crawler non viene quindi indicata come test di sicurezza. Prima della matrice viene mostrato un riepilogo numerico con request context scoperti, raggiungibili/in-scope, testati da almeno un'esecuzione concreta, solo discovery, saltati intenzionalmente, errori di esecuzione, 404/410 e percentuale di copertura; anonymous e authenticated hanno righe separate e, quando entrambi sono presenti, una riga totale. Nei report multi-entry aggregati la matrice mantiene anche il job/entry point di provenienza. La matrice e endpoint_coverage_summary vengono salvati nel JSON, nello snapshot .review.json e in Assessment_Results_Data_<ID>.json.

NOTE DI VALIDAZIONE RUNTIME
- Un profilo con cookie che la discovery dichiara non autenticato viene escluso dalla pianificazione autenticata; non sopprime la copertura anonima.
- ZAP considera completa la copertura attiva solo se casi pianificati, tentati, avviati e completati coincidono.
- Nikto con processo concluso ma copertura non verificabile viene registrato PARTIAL, non SUCCESS.
- La confidence finale dell'analisi AI viene applicata a tutti i candidate/vulnerability; Chromium puo' imporre un ceiling separato per XSS.
- Le richieste token (1) del provider AI Snap4City hanno timeout HTTP limitati.
