SECOPS INITIALIZER - GUIDA OPERATIVA
===================================

MANUALE OPERATIVO
-----------------

Questa guida contiene i comandi principali per installare, verificare e usare il progetto. I dettagli architetturali completi sono nel README e nella relazione.

1. PREPARAZIONE
---------------

Dalla root del progetto, per installare o verificare ambiente, scanner, Chromium e preflight:

  python initScript.py

Per aggiungere anche il laboratorio locale e la preparazione dei backend AI:

  python initScript.py --with-lab

Per stampare i comandi senza installare o avviare componenti:

  python initScript.py --commands-only

Per preparare un solo provider AI insieme al laboratorio:

  python initScript.py --with-lab --prepare-ai snap4city
  python initScript.py --with-lab --prepare-ai llama
  python initScript.py --with-lab --prepare-ai qwen

Snap4City è il provider remoto previsto dal progetto. Llama e Qwen usano Ollama locale.

Se Snap4City non ha ancora credenziali o token utilizzabili:

  python initScript.py --with-lab --prepare-ai snap4city \
    --snap4city-credentials snap4city_model_credentials.json

Le credenziali del provider AI sono separate da username, password e cookie del target.

2. PREFLIGHT
------------

Il preflight controlla runtime, server MCP, binari e dipendenze richieste dai wrapper.

Non usare --skip-scanners in un'installazione normale. Questa opzione serve solo quando si vuole inizializzare il progetto senza installare gli scanner.

Il browser è richiesto per le verifiche Chromium. --skip-browser lo rende opzionale e i controlli browser-only verranno saltati.

3. DRY-RUN
----------

Prima di un assessment lungo:

  python assessmentRunner.py \
    --config configs/dashboard-test.json \
    --orchestrator agentic \
    --mode balanced \
    --max-rounds 2 \
    --require-ai \
    --dry-run \
    --authorized

Il dry-run valida configurazione, scope e job. Non esegue scanner.

4. ASSESSMENT
-------------

Agentic BALANCED:

  python assessmentRunner.py \
    --config configs/dashboard-test.json \
    --orchestrator agentic \
    --max-rounds 2 \
    --mode balanced \
    --require-ai \
    --authorized

Deterministic BALANCED:

  python assessmentRunner.py \
    --config configs/dashboard-test.json \
    --orchestrator deterministic \
    --mode balanced \
    --authorized

Target diretto:

  python assessmentRunner.py \
    --target http://target \
    --orchestrator agentic \
    --mode balanced \
    --authorized

5. NUOVA APPLICAZIONE E CONFIGURAZIONE
-----------------------------------

Copiare configs/platform.example.json e modificare la copia:

  cp configs/platform.example.json configs/mio-target.json

Non creare il JSON da memoria. Impostare authorization.confirmed=true solo dopo aver verificato l'autorizzazione reale.

Campi minimi obbligatori:
  schema_version = 1
  platform.name
  assets[] con id e almeno un servizio
  ogni servizio con id e url, oppure protocol + port + base_path
  execution

Esempio minimo valido:

  {
    "schema_version": 1,
    "platform": {"name": "example-target"},
    "authorization": {
      "confirmed": true,
      "reference": "riferimento autorizzazione",
      "allow_same_host_ports": false,
      "discover_same_host_services": false
    },
    "assets": [{
      "id": "webhost",
      "host": "target.example",
      "services": [{
        "id": "http-main",
        "url": "http://target.example/",
        "auth_only": false,
        "allow_state_changes": false
      }]
    }],
    "execution": {
      "orchestrator": "agentic",
      "mode": "balanced",
      "request_rate": 10,
      "model": "snap4city",
      "max_rounds": 2,
      "require_ai": true,
      "allow_state_changes": false
    }
  }

Per login browser/OIDC aggiungere credentials e collegare il nome al servizio con credential_ref o credential_refs. Usare cookie_env, username_env e password_env invece di scrivere segreti nel JSON.

Esempio:
  "credentials": {
    "user": {
      "kind": "browser_oidc",
      "cookie_env": "SECOPS_TARGET_COOKIE",
      "username_env": "SECOPS_TARGET_USERNAME",
      "password_env": "SECOPS_TARGET_PASSWORD",
      "login_path": "/",
      "validation_path": "/",
      "optional": true
    }
  }

Poi nel servizio:
  "credential_ref": "user"

Prima di eseguire usare --dry-run. Per controllare soltanto login e sessione usare --auth-only.

6. SCOPE
--------

Default: same-origin.

--authorized-origin URL
  Aggiunge una origin HTTP o HTTPS esatta.

--allow-same-host-ports
  Autorizza HTTP o HTTPS su altre porte dello stesso hostname esatto.

--discover-same-host-services
  Cerca servizi web sullo stesso hostname. Richiede l'autorizzazione multi-porta.

Queste opzioni non autorizzano host sibling.

7. RATE E STATE CHANGES
-----------------------

Il rate operativo normale è 10 request start/s.

Il parallelismo non deve aumentare il picco di traffico. Il pacer è condiviso anche tra processi dello stesso utente sulla VM. Run concorrenti sullo stesso target restano sconsigliati perché duplicano lavoro e possono contendere scanner stateful.

--no-allow-state-changes
  Mantiene bloccati probe distruttivi o non necessari.

--allow-state-changes
  Abilita probe state-changing limitati da budget e policy per un run esplicitamente autorizzato.

8. AUTENTICAZIONE
-----------------

Sono supportati anonymous, cookie e browser/OIDC.

Con --target diretto, --cookies passa la sessione primaria e --secondary-cookies aggiunge una seconda identità. Con --config è preferibile usare credentials e credential_ref/credential_refs.

Le sessioni sono separate per identità e radice applicativa.

Per controllare solo l'autenticazione:

  python assessmentRunner.py \
    --config <config.json> \
    --orchestrator agentic \
    --mode balanced \
    --auth-only \
    --authorized

Un rifiuto conclusivo delle credenziali blocca submit ripetuti. Errori tecnici possono essere ritentati dopo cooldown.

9. DISCOVERY
------------

La discovery usa crawler HTTP, Chromium, JavaScript, request contract, FFUF, Arjun, ZAP e service discovery quando autorizzata.

La superficie viene divisa in famiglie. Le nuove famiglie ricevono priorità iniziale per evitare che una sola area molto grande saturi la coda.

FFUF, Arjun e ZAP possono ampliare il grafo delle richieste osservate. Nel percorso Agentic devono essere selezionati dal modello. Nel percorso Deterministic possono essere previsti dalla pipeline.

Limiti principali:

  TEST      HTTP 8/16        Browser 4/8         Script 12
  FAST      HTTP 360/1200    Browser 220/700     Script 640
  BALANCED  HTTP 2500/8000   Browser 1500/5000   Script 4000
  DEEP      HTTP 6000/18000  Browser 3500/10000  Script 8000

I valori base/max sono ceiling. La discovery può terminare prima quando non produce nuova superficie.

10. AGENTIC E LANGGRAPH
----------------------

L'Agentic costruisce azioni concrete dalla discovery. Il modello decide quali azioni eseguire e la loro priorità.

Python applica scope, safety, compatibilità, rate e budget.

Il planner divide i cataloghi grandi in batch. Un batch troppo grande viene spezzato senza perdere candidati. Metadati storici possono essere compattati, ma non l'azione concreta.

Con --require-ai, un planning obbligatorio non riuscito viene segnalato come errore.

Round e budget planner:

  TEST      1 round   24 reference actions    120 s/round     120 s cumulativi
  FAST      2 round   180 reference actions   1800 s/round    3600 s cumulativi
  BALANCED  2 round   480 reference actions   3600 s/round    7200 s cumulativi
  DEEP      3 round   720 reference actions   5400 s/round    16200 s cumulativi

Le reference actions non sono hard cap di coverage nei profili normali.

11. PROFILI E BUDGET
--------------------

  TEST      execution 1,5 h   verification 10 min   analysis 10 min   report 20 min   watchdog 3 h
  FAST      execution 16 h    verification 60 min   analysis 120 min  report 60 min   watchdog 24 h
  BALANCED  execution 48 h    verification 120 min  analysis 360 min  report 120 min  watchdog 66 h
  DEEP      execution 96 h    verification 240 min  analysis 720 min  report 240 min  watchdog 128 h

TEST è diagnostico. BALANCED è il profilo consigliato per assessment normali.

13. REPORTING
-------------

Il report produce JSON, HTML e PDF.

JSON contiene il dataset completo.
HTML è pensato per la consultazione.
PDF è una sintesi di consegna.

Il report separa finding, stato di esecuzione e coverage.

Nel Deterministic il testo dei finding deriva dal tool o dal wrapper. Il reporting può completare campi mancanti solo per vulnerability confermate con regole conservative.

Nell'Agentic la final analysis può produrre descrizione, impatto e remediation per vulnerability e candidate. L'evidenza originale resta invariata.

I batch dell'analisi AI vengono divisi se superano la finestra di contesto. Un finding molto grande viene compattato solo nella copia inviata al modello.

Payload di report molto grandi vengono compressi e trasferiti a chunk. Se il trasporto normale fallisce, il fallback locale usa la stessa struttura materializzata. La coverage non viene ridotta per rendere il report più piccolo.

16. TROUBLESHOOTING
-------------------

Login fallito
  Verificare configurazione, credenziali e redirect OIDC.

Molti auth precheck falliti
  Verificare la sessione sulla specifica radice applicativa.

Discovery con coda residua
  Controllare limiti, pagine lente e se la coda di discovery sta ancora producendo nuovi endpoint.

Planner fallito
  Controllare provider, budget e diagnostica dei batch.

Tool partial
  Leggere il codice diagnostico e il timeout.

PDF mancante
  Usare JSON e HTML già prodotti e controllare il renderer.

Rate sotto 10 req/s
  Il valore è un massimo. Pagine lente o tool seriali possono non saturarlo.

17. OPZIONI initScript
----------------------

--with-lab
  Avvia o verifica il laboratorio locale e abilita la preparazione dei backend AI.

--prepare-ai all|snap4city|llama|qwen
  Sceglie quali backend preparare insieme a --with-lab.

--agentic-model snap4city|llama|qwen
  Sceglie il modello usato dall'esempio Agentic e, se --prepare-ai è omesso, il backend da preparare.

--snap4city-credentials FILE
  Indica il file credenziali del provider Snap4City. Non sono credenziali del target.

--mode test|fast|balanced|deep
  Sceglie il profilo usato dagli esempi e dall'eventuale --run.

--run none|deterministic|agentic
  Esegue il DVWA del laboratorio dopo l'inizializzazione. Richiede --with-lab per deterministic o agentic.

--skip-preflight
--skip-scanners
--skip-browser
--require-browser
  Opzioni di installazione e diagnostica. Non usare gli skip in una installazione normale.

--commands-only
  Stampa la guida senza installare o avviare componenti.

18. OPZIONI assessmentRunner
----------------------------

--config FILE
--target URL
--cookies COOKIE_HEADER
--secondary-cookies COOKIE_HEADER
--orchestrator agentic|deterministic
--mode test|fast|balanced|deep
--model snap4city|llama|qwen
--max-rounds 1|2|3
--auth-only
--authorized
--authorized-origin URL
--allow-same-host-ports
--no-allow-same-host-ports
--discover-same-host-services
--no-discover-same-host-services
--allow-state-changes
--no-allow-state-changes
--require-ai
--no-require-ai
--dry-run
--only JOB_ID
--stop-on-error

Per l'elenco aggiornato: python assessmentRunner.py --help
Per installazione e preflight: python initScript.py --help

Usare soltanto target propri o esplicitamente autorizzati.
